# State Machines

## Order Status (`order_status`)

Життєвий цикл за [TD-0011](../designs/TD-0011-order-status-flow.md): статус рухають факти
(ТТН, трекінг Нової Пошти, оплата), адмін лише вирішує. Правила — одна таблиця в коді
(`fillando-be/src/modules/order/helpers/order-status.rules.ts`), через яку йдуть усі записи.

```
                 ┌─────────┐
                 │   NEW   │ ◄── створення замовлення
                 └────┬────┘
   написав клієнту    │ ⇅ (до відправки три статуси вільно міняються)
                 ┌────▼───────┐
                 │ PROCESSING │  «Очікує підтвердження»
                 └────┬───────┘
   клієнт підтвердив  │ ⇅
                 ┌────▼──────┐
                 │ CONFIRMED │
                 └────┬──────┘
   ТТН (з будь-якого  │      самовивіз: «Видано»
   з трьох)      ┌────▼────┐ ──────────────┐
                 │ SHIPPED │               │
                 └──┬───┬──┘               │
   НП «отримано»    │   │ НП відмова /     │
                    │   │ припинено        │
           ┌────────▼┐ ┌▼──────────┐       │
           │DELIVERED│◄┤ RETURNING ├──► RETURNED
           └────┬────┘ └───────────┘
    PAID ⇅      │  (зняття PAID повертає)
           ┌────▼──────┐
           │ COMPLETED │
           └───────────┘

   NEW / PROCESSING / CONFIRMED ──► CANCELLED ── «Відновити» ──► NEW
```

### Дозволені переходи

| З | В | Хто | Коментар |
|---|---|---|---|
| `NEW` ⇄ `PROCESSING` ⇄ `CONFIRMED` | | адмін | Написав клієнту → «Очікує підтвердження»; клієнт підтвердив → «Підтверджено». Три статуси до відправки міняються вільно, щоб помилковий клік відкочувався тим самим списком |
| `NEW`, `PROCESSING`, `CONFIRMED` | `SHIPPED` | ТТН | `PATCH /orders/:id/ttn` — тим самим записом, для будь-якого способу доставки (ТТН на самовивозі = все ж відправили) |
| `NEW`, `PROCESSING`, `CONFIRMED` | `DELIVERED` | адмін | «Видано» — лише самовивіз |
| `NEW`, `PROCESSING`, `CONFIRMED` | `CANCELLED` | адмін | Скасування до відправки |
| `SHIPPED` | `DELIVERED` | трекер / адмін | НП «отримано»; адмін — запасний шлях, коли трекер посилку не бачить |
| `SHIPPED` | `RETURNING` | трекер / адмін | Відмова, припинення зберігання |
| `DELIVERED`, `COMPLETED` | `RETURNING` | адмін | Повернення товару після вручення |
| `RETURNING` | `RETURNED` | адмін | «Повернення отримано» — посилка в магазині (термінальний) |
| `RETURNING` | `DELIVERED` | адмін | «Клієнт забрав» — передумав після відмови |
| `CANCELLED` | `NEW` | адмін | «Відновити» — флоу починається знову |
| `DELIVERED` ⇄ `COMPLETED` | | система | Інваріант: `COMPLETED` ⇔ доставлено **і** `PAID`. Що з двох настало другим, той запис і переводить. Вручну `COMPLETED` не ставиться |

- **Відправлене не скасовується** (`SHIPPED → CANCELLED` заборонено) — це повернення.
- **Валідація реалізована:** адмінський `PATCH /orders/:id/status` приймає лише переходи з
  `allowed_status_transitions` (поле адмінської відповіді `GET /orders/:id`), інакше
  `409 INVALID_STATUS_TRANSITION`. Запис умовний на прочитані статуси — паралельна зміна
  дає `409 ORDER_STATUS_CHANGED`.
- **Історія:** кожна зміна `order_status` і `payment_status` дописується в `status_history`
  тим самим оновленням (`$push`), з `actor` (`admin` / `customer` / `tracker` / `gateway` /
  `system`) і приміткою (ТТН, код НП).
- **`PROCESSING` змінив зміст.** Було «В обробці» (підтверджено, збирається) *після* `CONFIRMED`;
  стало «Очікує підтвердження» (адмін написав клієнту) *перед* ним. Старі записи з `PROCESSING`
  одноразова міграція (запускалася власником під час релізу, у репо не зберігається) переводить у `SHIPPED`
  (є ТТН) або `CONFIRMED` (немає); відрізняє їх за відсутністю запису в `status_history`.
- **Адмінка:** випадаючий список з усіма статусами, недозволені з поточного — неактивні
  (`SHIPPED` і `COMPLETED` неактивні завжди).

**Побічний ефект:** перехід у `CANCELLED` чи `RETURNED` (і розскасування) змінює
`payment_status` — див. [Крос-машинне правило: скасування або повернення](#крос-машинне-правило-скасування-або-повернення).

**Автоматичні переходи (відстеження Нової Пошти, щогодини):** «отримано» → `DELIVERED`
(оплачене — одразу `COMPLETED`; накладний платіж з `PENDING` — тим самим записом `PAID` і
`COMPLETED`, бо покупець заплатив на відділенні); відмова / припинення зберігання → `RETURNING` +
лист адміну; видалено / ТТН не знайдено — лише лист. Для інших способів оплати `payment_status`
робот не змінює. Деталі — FRD §9.2.

## Payment Status (`payment_status`)

```
                    ┌─────────┐
                    │ PENDING │ ◄── створення замовлення (завжди)
                    └────┬────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
     ┌────▼──┐      ┌────▼───┐     ┌────▼───┐
     │ PAID  │      │ FAILED │────►│ VOIDED │ ◄── order_status → CANCELLED
     └───┬───┘      └────────┘     └────────┘
         │
    ┌────▼─────┐
    │ REFUNDED │
    └──────────┘
```

### Дозволені переходи

| З | В | Коментар |
|---|---|----------|
| `PENDING` | `PAID` | Оплата підтверджена (LiqPay callback автоматично; трекер НП для накладного платежу, коли посилку отримано; адмін вручну для IBAN/CASH/COD) |
| `PENDING` | `FAILED` | Оплата не пройшла (LiqPay callback зі статусом failure/error) |
| `PENDING` | `VOIDED` | Замовлення скасоване, кошти не надходили — виставляється **автоматично** |
| `FAILED` | `VOIDED` | Те саме: скасування замовлення після невдалої оплати — **автоматично** |
| `PAID` | `REFUNDED` | Повернення коштів (вручну, після реального рефанду) |
| `PENDING`, `FAILED` | `VOIDED` | Неоплачена посилка повернулася (`order_status → RETURNED`, TD-0011) — **автоматично** |
| `VOIDED` | `PENDING` | Розскасування замовлення (`CANCELLED → NEW`) — **автоматично** |
| `FAILED` | `PENDING` | Два джерела, обидва **автоматичні**. (1) Клієнт змінив спосіб оплати з LiqPay на офлайн (`PATCH /orders/lookup/:n/payment-method`, `PATCH /orders/me/:id/payment-method`): відхилена спроба карткою не є фактом про IBAN/COD/CASH-замовлення. (2) Клієнт відкрив повтор оплати карткою і клейм видано (`POST /liqpay/checkout`, з 2026-09-08): сесія знову жива, тож і статус знову `PENDING` — це те, що не дає другій вкладці відкрити другу сесію. Див. [TD-0009](../designs/TD-0009-customer-payment-method-change.md) і абзац про одну живу сесію нижче |

**Note:** Для IBAN/CASH оплата підтверджується адміном вручну (`PATCH /orders/:id/payment-status`). Для **накладного платежу** (`COD`) замовлення лишається `PENDING` увесь час доставки, а щойно трекер Нової Пошти бачить «отримано», оплата стає `PAID` тим самим записом, що й `COMPLETED` (TD-0011): покупець заплатив на відділенні. Адмін може поставити `PAID` і раніше. Встановлення ТТН оплату не змінює. Для **LiqPay** підтвердження автоматичне: server-to-server callback `POST /liqpay/callback` переводить `PENDING → PAID` (ідемпотентно, з перевіркою підпису та суми) і надсилає лист. Див. [ADR-0009](../adr/0009-online-payment-liqpay.md).

**Note:** `VOIDED` («Скасовано») означає, що оплата вже не очікується, бо замовлення скасоване і кошти не надходили. Це не те саме, що `REFUNDED` — той описує реальне повернення вже отриманих коштів. Див. [TD-0003](../designs/TD-0003-order-cancellation-payment-status.md).

## Крос-машинне правило: скасування або повернення

`order_status` і `payment_status` — незалежні машини станів з двома винятками: скасування чи
повернення замовлення (нижче) і `COMPLETED` = `DELIVERED` + `PAID` (вище). Будь-яка зміна
`order_status` разом перераховує `payment_status` за таблицею нижче.

| `order_status` | Поточний `payment_status` | Новий `payment_status` | Чому |
|----------------|---------------------------|------------------------|------|
| → `CANCELLED` / `RETURNED` | `PENDING` | `VOIDED` | Кошти не надходили — оплата вже не очікується (типово: відмова від накладного платежу) |
| → `CANCELLED` / `RETURNED` | `FAILED` | `VOIDED` | Те саме; `FAILED` перестає бути актуальним |
| → `CANCELLED` / `RETURNED` | `PAID` | **не змінюється** | Гроші реально отримані. Адмін виконує повернення і вручну ставить `REFUNDED` |
| → `CANCELLED` / `RETURNED` | `REFUNDED` | **не змінюється** | Уже термінальний |
| `CANCELLED` → `NEW` | `VOIDED` | `PENDING` | Розскасування: оплата знову очікується |

**Пізній callback платіжного шлюзу.** Якщо LiqPay підтверджує оплату вже після скасування замовлення (`POST /liqpay/callback` → `applyGatewayPaymentResult`):

- `success`/`sandbox` → `payment_status` стає `PAID` і зберігається `payment_transaction_id` (кошти реально надійшли, приховувати їх не можна), але **клієнтський лист «оплату отримано» не надсилається** — замість нього йде service-лист адміну про потребу повернення. `order_status` лишається `CANCELLED`.
- `failure`/`error` → нічого не змінюється, `VOIDED` зберігається.

## Крос-машинне правило: зміна способу оплати клієнтом

Покупець може перевести **неоплачене** замовлення (`payment_status ∈ {PENDING, FAILED}`,
`order_status ∈ {NEW, PROCESSING, CONFIRMED}` — ще без ТТН) з LiqPay на `COD` / `IBAN` / `CASH` (з тим самим правилом
сумісності з доставкою, що й на чекауті — тепер серверним: `CASH` лише `PICKUP`, `COD` лише
`NOVA_POST`/`COURIER`). Щойно внесено ТТН (замовлення стає `SHIPPED`, TD-0011), посилка може
нести накладну накладного платежу, тож далі спосіб міняє лише адмін. Запис умовний і пінить прочитаний стан разом із поточним методом:
callback або друга вкладка, що встигли між читанням і записом, роблять його промахом (перечит →
або той самий метод уже стоїть = no-op, або `409 PAYMENT_METHOD_LOCKED`). Див.
[TD-0009 §5.4.1](../designs/TD-0009-customer-payment-method-change.md).

**Пізній callback LiqPay після зміни способу оплати.** LiqPay знає лише номери, які ми віддали йому,
коли замовлення було LiqPay-замовленням, тож callback для іншого методу означає, що покупець змінив
метод під час живої сесії. Кожен запис callback-у пінить метод:

| Callback | `payment_method` зараз | Результат |
|---|---|---|
| `failure`/`error` | `≠ LIQPAY` | нічого не змінюється — мертва карткова сесія не має зробити COD-замовлення `FAILED` |
| `success`/`sandbox` | `≠ LIQPAY` | `payment_status = PAID`, **`payment_method` повертається на `LIQPAY`** (гроші реально прийшли карткою), `payment_transaction_id` зберігається; клієнту — лист «оплачено», сервісу — лист «не збирати накладний платіж/IBAN». Якщо `order_status` уже поза `NEW`/`CONFIRMED`, сервісний лист має тему «ТЕРМІНОВО … зняти … на ТТН №…» — єдиний запобіжник від повторної оплати на пошті — людина |

**Одна жива сесія LiqPay на замовлення.** `POST /liqpay/checkout` клеймить сесію умовним записом
`liqpay_checkout_started_at`: доки платіж `PENDING`, друга сесія в межах 15 хв відхиляється
(`409 LIQPAY_SESSION_ACTIVE` з `retry_after_seconds`); `FAILED` — сесія, яку LiqPay сам закрив,
повтор дозволений одразу. Той самий залишок часу lookup віддає як `liqpay_retry_after_seconds`.
Адмінська зміна `payment_method` скидає штамп.

**Доповнення 2026-09-08 (аудит блоку I, рядки I-e, I-18).** Виданий клейм повтору сам переводить
`FAILED → PENDING` тим самим умовним записом (джерело переходу — `POST /liqpay/checkout`, не
адмінка й не callback). Перший повтор після невдачі лишається доступним **одразу**, як вирішено в
TD-0009 §5.4.3, але щойно payload виданий, замовлення читається як `PENDING` зі свіжим штампом —
тож друга вкладка вже не відкриє другу живу сесію для того самого повтору. Ціна цього видима:
покупець, який відкрив повтор і покинув його, чекає ті самі 15 хв (або міняє спосіб оплати) — та
сама прийнята ціна, що вже діяла для першої спроби. Реквізити провайдера читаються **до** клейму,
тож недоступний шлюз відповідає `503 LIQPAY_UNAVAILABLE` і не лишає покупцю годинника за сесію,
якої не було.

## Product Variant Status (`status`)

```
  ┌───────┐
  │ DRAFT │ ◄── створення (якщо вказано)
  └───┬───┘
      │
  ┌───▼────┐
  │ ACTIVE │ ◄── за замовчуванням при створенні
  └───┬────┘
      │
  ┌───▼──────┐
  │ ARCHIVED │
  └──────────┘
```

| Статус | В каталозі | В замовленні |
|--------|-----------|-------------|
| `draft` | Не показується | Не можна додати |
| `active` | Показується | Можна додати |
| `archived` | Не показується | Існуючі замовлення зберігаються |

Фільтр каталогу: `status = "active"` (hardcoded в агрегації).

## Discount Coupon Lifecycle

```
  Створення (адмін)
       │
       ▼
  ┌──────────────┐
  │  is_active   │ ◄── true за замовчуванням
  │  valid_until │ ◄── дата закінчення
  └──────┬───────┘
         │
    Валідація при checkout:
         │
         ├── code не знайдено      → { valid: false, reason: "NOT_FOUND" }
         ├── is_active = false     → { valid: false, reason: "INACTIVE" }
         ├── valid_until < now     → { valid: false, reason: "EXPIRED" }
         └── все ок                → { valid: true, coupon: {...} }

    При створенні замовлення:
         │
         └── Snapshot в order.applied_discount:
             { coupon_id, code, discount_percent, discount_amount }
```

**Note:** Купон не має лічильника використань — один код можна використати необмежену кількість разів до закінчення терміну дії або деактивації адміном.
