# Functional Requirements Document (FRD)

## Fillando — Інтернет-магазин витратних матеріалів для 3D-друку

**Дата:** 22.04.2026
**Версія:** 1.0
**Стек:** NestJS (MongoDB) + Next.js 16 (React 19, TypeScript, Tailwind CSS 4)


**Нова головна й шапка, бренд за замовчуванням, адмінка однаково, 09.11.2026 — лише локально, не production (рішення власника, TD-0015):**
- **Головна** — вітрина за структурою маркетплейсу: перший ряд «меню категорій · банер · картка праворуч», під ним «Новинки» одним рядом зі стрілками, смуга (типово «Прайс-лист») і добірки «Вітрини» сіткою. Меню — «Акції» (лише поки є акційні товари) і «Новинки» (ведуть до відповідних стрічок на `/catalog`), до 10 категорій першого рівня публічного дерева в його порядку з фото категорії як іконкою, далі «Усі товари» й «Прайс-лист»; на телефоні його немає (дерево — у «Меню» шапки). Банер має абстрактний анімований фон «Аврора»: зупиняється поза екраном і у фоновій вкладці, за «менше руху» — один нерухомий кадр, без WebGL — градієнт тих самих кольорів. Заголовок банера — H1 сторінки. Прибрано героя з картинкою філаменту, плитки категорій, смугу логотипів брендів, «Чому Fillando» й оптовий блок унизу: про конкретний товар у коді головної не лишилось нічого.
- **«Вітрина»** редагує всі тексти головної тією самою кнопкою «Зберегти вітрину»: смужку над шапкою (до 4 рядків по 60 символів; без рядків смужки немає), банер (надзаголовок, заголовок 1–80, виділена частина заголовка, текст до 200, кнопка), картку праворуч (заголовок, текст, кнопка, що відкриває форму оптової заявки або сторінку сайту) і смугу між стрічками (можна вимкнути). Адреси кнопок — лише сторінки цього сайту (починаються з «/»), текст — без HTML. До першого збереження сервер віддає типові тексти. Вибір плиток категорій для головної прибрано з «Вітрини» й API (`home_category_ids`); перше збереження прибирає старе поле з бази.
- **Шапка на всіх сторінках вітрини:** смужка з умовами й телефоном, логотип, «Каталог» (та сама панель дерева), широкий пошук із кнопкою «Знайти», «Кабінет» (вхід або меню користувача) і «Кошик» з лічильником; на телефоні — «Меню · логотип · Кабінет · Кошик», під ними пошук. «Прайс-лист», «Опт», FAQ і «Контакти» — у підвалі й мобільному меню. Шрифти вітрини — Onest (текст) і Unbounded (заголовки головної й логотип); адмінка лишається на Inter.
- **Бренд:** нова товарна категорія (створена чи перетворена з групи) одразу має характеристику «Виробник» — текст, призначення «Бренд», обов'язкова, у фільтрах і в таблиці сторінки товару; далі її можна змінити, як будь-яку. Редактор категорії попереджає, якщо обов'язкової характеристики з призначенням «Бренд» немає: такі товари не потраплять у Google Merchant. «Призначення» можна змінити й на вже заповненій характеристиці, крім переходу в «Колір» і з нього. Плашки бренду над назвою товару більше немає: бренд — рядок таблиці, якщо стоїть галочка «У таблиці на сторінці товару»; міграція філаменту більше не ховає «Виробник» з таблиці. Фід, розмітка й GA4 беруть бренд як раніше.
- **Адмінка:** поля нового каталогу й «Вітрини» мають вигляд спільного поля адмінки; на сторінці категорії й товару одна закріплена шапка з «Зберегти» (і «Опублікувати» для категорії) замість кнопок у кожному блоці; «Вітрина» — у загальному вигляді адмінки.
- **Аудит 08.11:** `release-check` більше не пропускає непрацюючий partner API чи відхилений токен/cookie (SKIP — лише без токена), а `catalog-release.mjs` зупиняється на таких помилках ще до міграції; від'ємна межа числової характеристики в адресі фільтра (`f.temperature.min=-20`) більше не дає 404 (ціна лишається невід'ємною); посадкова сторінка не приймає умову «лише акційні» (`on_sale`), яку раніше мовчки губила. Репетиція міграції на свіжому дампі 08.11 з обома токенами — ALL CHECKS PASSED (83 PASS, 0 SKIP).

**Без звʼязку «рефіл ↔ на котушці», 04.11.2026 — лише локально, не production (рішення власника):** функцію прибрано повністю. В адмінці товару немає блоку «Інша комплектація (рефіл / на котушці)», у вигляді категорії — підпису іншої комплектації; API `/products/:id/admin/relations` немає; міграція філаменту не пише `relations`. На сторінці рефілу лишаються попередження й позначка «Без котушки» на фото, але немає рядка «на котушці — X ₴» і кнопки переходу на котушку (`spooled_counterpart` більше не віддається). Збережені в базі `spooled_product_id` / `relations` ніхто не читає. У production посилання є до релізу.

**Споживачі каталогу й репетиція релізу, 28.10.2026 — лише локально (стенд і копія дампу 27.10), не production:** партнерський API (категорії, артикули, картки, наявність), PDF оптового прайс-листа й публічний прайс-лист працюють за наявності нових категорій: показують лише публічні товарні категорії та їхні товари, а товари нової структури віддають у попередньому форматі (характеристики текстом, бренд із «Виробник», колір варіанта як раніше). На мігрованому філаменті результат збігається зі станом до міграції, окрім партнерських карток товарів із кольоровою віссю: рядок «Колір» на рівні товару тепер називає колір самого варіанта (українською зі словника), а не застарілу копію кольору одного з варіантів (рішення власника 28.10; на копії дампу виправлено значення в 270 із 293 карток, формат той самий). Кнопка «Прайс-лист» доступна в новій адмінці товарів. Синхронізація з Promом оновлює ціну й наявність і для нової структури, а під час службової операції каталогу відкладає запис до наступного запуску («Відкладено»); у новому редакторі є «ID на Промі» й «Артикул вендора» для наявних, нових варіантів і нових товарів. Фільтри нової вітрини показують значення з нульовою кількістю (список не «стрибає»), `/catalog` додано в sitemap. Репетиція на копії дампу: міграція ~2,7 с, вітрина/фасети/фід/sitemap/PDF/прайс-лист збігаються з legacy, сценарій покупця до оформлення, SEO-статуси, заміри навантаження, відкат побайтово. Додатково (28.10): на копії дампу в окремому MongoDB пройдено production-режим інструментів релізу — міграція лише з явною адресою бази з середовища, назвою `fillando-prod`, підтвердженням кожного запису й перевіреним backup, команда ввімкнення записів нової адмінки; нова адмінка редагує мігрований філамент (зміну видно на сторінці товару); оформлено одне справжнє замовлення на мігрованих даних (лист на службову адресу), після прибирання й відкату дані побайтово дорівнюють дампу. Редактор зберігає порядок характеристик товару. Вітрина: шапка має один пункт «Каталог» з панеллю всього дерева (посилання в серверному HTML), бокові фільтри нової вітрини — у картці, «Ціна» й «Наявність» першими, діапазони — зі слайдером; під час переходу між сторінками — тонка смуга прогресу (без skeleton, справжні 404/308 збережено). Чернетка runbook релізу — `docs/runbooks/catalog-v2-release.md`. Нова адмінка також переносить товар в іншу товарну категорію нового каталогу: сервер пропонує, які характеристики переходять (за ключем або, для скопійованої категорії, за назвою й типом), показує втрати (їх треба підтвердити) і обов’язкові значення цілі; адреси, артикули, ціни й залишки не змінюються, у неопублікованій цілі варіанти стають чернетками. Порожню чернетку категорії можна видалити або змінити її тип (група ↔ товарна); непорожню — лише після явного перенесення товарів і підкатегорій. Посадкові сторінки категорії нового каталогу редагуються разом із нею (Categories → категорія → «Посадкові сторінки»): тексти, FAQ, закріплені фільтри (значення характеристик, родини кольорів), порядок і статус; опублікувати можна лише сторінку з активними товарами, адреса опублікованої сторінки не змінюється звичайним збереженням, дублікати фільтрів у межах категорії відхиляються, видалити можна лише чернетку. Кількість товарів на плитках лендінгів рахується так само, як вітрина. У категорії нового каталогу (чернетці чи опублікованій) адмін задає title, опис для пошуку, H1 і тексти над/під товарами з попереднім переглядом сніпета; без них вітрина використовує типові значення. Сторінка адмінки «Вітрина» задає плитки категорій на головній, добірки (стрічка товарів категорії або її посадкової сторінки з переходом) і текст над `/catalog`; покупець бачить лише опубліковане. Переходи «до каталогу» (порожній кошик, після замовлення, головна) ведуть на `/catalog`. Для товарної категорії нового каталогу адмін задає правила Google-фіду: категорію таксономії Google, характеристики в назві й у `product_highlight`, статичні мітки кампаній; категорія без правил (філамент) експортується як раніше. Розмір і матеріал у фіді беруться лише з характеристик із відповідним значенням (семантикою). Адресу товару (варіанта), категорії чи посадкової сторінки нового каталогу можна змінити лише окремою дією «Змінити адресу»: стара адреса назавжди перенаправляє на нову одним постійним перенаправленням (параметри запиту зберігаються), без ланцюжків; звичайне перейменування адрес не змінює; зарезервовані адреси сайту й адреси інших об’єктів (зокрема старі) зайняти не можна. Рефіл у новому каталозі — явний зв’язок з товаром «на котушці»: адмін вибирає товар і підтверджує, який варіант рефілу відповідає якому варіанту котушки (підказка — той самий колір зі словника); сторінка рефілу показує актуальну ціну парного варіанта, а без пари — «від» найдешевшого активного. Попередження перед покупкою (як «Це рефіл — без котушки»), позначка на фото, назва іншої комплектації, порядок, приховування й виділення характеристик картки задаються в категорії («Картка товару»), а не в коді вітрини; міграція філаменту переносить їх так, що картка рефілу не змінюється. Сторінка товару нового каталогу описує варіанти для пошукових систем як групу (колір, розмір або матеріал) з посиланнями на інші варіанти; інші осі (наприклад, струм) подаються як характеристика товару, а матеріал у розмітці той самий, що й у Google-фіді. Події аналітики (перегляд товару, додавання в кошик — зі сторінки товару, картки каталогу й прайс-листа, початок оформлення, покупка) передають артикул товару; покупка звітується лише для конкретного номера замовлення й один раз (повторне відкриття сторінки «Дякуємо» не дублює конверсію). У великому розділі (понад 100 товарних категорій) фільтр «Категорія» в боковій панелі показує лише вже вибрані категорії — перехід у підкатегорії робиться плитками.

**Нова адмінка після міграції — не гірше за стару, 29.10.2026 — лише локально (стенд і копія дампу 27.10), не production:** опубліковану категорію нового каталогу (після релізу — «Філамент») можна перейменувати, змінити зображення плитки й порядок у меню; її характеристики редагуються на місці: нова характеристика, назва, порядок, одиниця (з 31.10 — лише поки значення характеристики немає в жодному товарі чи SKU: інакше адмінка блокує поле й показує, скільки товарів його мають, бо значення не перераховуються), «У характеристиках товару», фільтри та варіанти списку. Зміна відхиляється з поясненням і точною кількістю зачепленого (товарів, артикулів, посадкових сторінок, налаштувань картки чи фіду), якщо вона зламала б наявні дані: зміна типу, «кількох значень» або призначення характеристики, яку вже використовують; видалення використаної характеристики чи варіанта списку; вимкнення фільтра, закріпленого на посадковій сторінці; обов’язкова характеристика, якої ще немає в товарах опублікованої категорії. Адмінка показує, що використовує кожна характеристика, і заздалегідь блокує лише такі зміни; збережене одразу діє на сайті й у фіді. Переміщення в іншу групу й видалення — як і раніше, лише для чернетки. Також у новій адмінці: словник кольорів (додати, змінити — назви й родина варіантів цього кольору оновлюються разом, адреси не змінюються; видалити лише невикористаний, з кількістю варіантів у відмові), акції товару (на кожен варіант або «на весь товар», з попереднім переглядом ціни й попередженням про ціну нижчу за закупівельну; завершена акція не заважає зберігати), зміна постачальника, «Архівувати всі варіанти», видалення варіанта чи товару, якого ще не продавали (без замовлень, кошиків, зв’язків і старих адрес; активні спершу архівуються), завантаження фото плитки посадкової сторінки. Повторна публікація категорії з кольоровою віссю більше не лишає її товари чернетками. Повторна репетиція релізу на копії дампу в окремому MongoDB (production-режим, mapping 28.10 зі зв’язком рефілу й попередженням): міграція 2,5 с, правка філаменту в новій адмінці, відкат відмовив, доки правку не повернули, потім відкат 2,2 с і дані побайтово дорівнюють дампу.

**Дерево й вітрина без обмежень першого релізу, 29.10.2026 (друга сесія) — лише локально (стенд), не production:** опубліковану категорію можна перенести в іншу опубліковану групу або в корінь (у неопубліковану — ні, бо вона зникла б із сайту); адреси категорії, її посадкових сторінок і товарів від розташування не залежать, змінюються лише меню й крихти. Товарну категорію з товарами можна перетворити на групу лише за явним планом: адмін розподіляє кожен товар (з усіма варіантами) і кожну посадкову сторінку в інші товарні категорії, сервер без запису перевіряє план (жодне значення характеристик не губиться, вісь варіантів і обов’язкові значення цілі, закріплені фільтри сторінок у характеристиках цілі, унікальність адрес) і показує попередження (варіанти, що стануть чернетками в неопублікованій цілі, сторінки без товарів, налаштування картки й фіду, що не переносяться); виконується лише перевірений план однією операцією: категорія стає групою з тією самою адресою, товари зберігають адреси, артикули, ціни й залишки, стара адреса опублікованої посадкової сторінки постійно перенаправляє на нову, добірки вітрини йдуть за сторінкою, цільові категорії за бажанням переходять у нову групу. Добірка на головній («Вітрина») може бути явним списком товарів (до 24, у заданому порядку): головна показує їхні варіанти лише з опублікованих категорій, товари в наявності першими; товар, що є в добірці, не видаляється. Бренди на головній і бренд-сутність прибрано з обсягу (рішення власника 29.10: «Виробник» лишається характеристикою). Перевірка релізу на копії дампу в production-режимі виявила й виправила два дефекти: лістинг нової вітрини не ставив товари в наявності першими (перша сторінка «Філаменту» відрізнялась би від поточної), а Google-фід після міграції лишався недоступним до перезапуску — тепер він перебудовується сам за кілька секунд.

**Великий каталог, 29.10.2026 (третя сесія) — лише локально (синтетичний каталог і стенд), не production:** покупець бачить ті самі ціни, порядок («в наявності першими», порядок добірки), склад лістингів і sitemap, змінилась лише швидкість і форма sitemap. На каталозі з 10 000 категорій і 100 000 товарів «весь каталог» (`/catalog`, сторінки 1–40, три сортування) відповідає за p95 ≈ 0,3 с при 10 одночасних покупцях (було 3,3 с); переміщення категорії в адмінці (опублікованої й чернетки) — до 1 с. Sitemap: поки адрес менше ~20 000 (поточний магазин) `/sitemap.xml` — той самий один файл; більше — `/sitemap.xml` стає індексом файлів `/sitemap/<n>.xml` (кожен менше 50 000 адрес, усі з одного стану каталогу), robots.txt і далі вказує на `/sitemap.xml`. Головна читає лише категорію «Філамент» для героя, а не список усіх категорій. ~~Відомі межі на такому розмірі: генерація Google-фіду при старті тримає в пам’яті всі товари (~518 MiB на 100 000), старий список `GET /categories` і панель «Каталог» у шапці не масштабуються понад ~100 товарних категорій~~ — закрито 30.10 (нижче).

**Рішення власника за аудитом, 31.10.2026 — лише локально, не production:** межі повзунків ціни й числових характеристик — по всій категорії, хоч які ще фільтри обрані (як у попередньому каталозі): межі не стрибають після кожного кліку, обраний діапазон не зсувається; лічильники значень, як і раніше, рахуються за звуженим лістингом. Перехідно (до baseline Search Console): старі адреси сторінок лістингу з 12 товарами на сторінці, що тепер за межами (`?page=20`), один раз перенаправляються на сторінку з тими самими першими товарами (`?page=10`), а `?limit=36` — на 48; якщо й та сторінка за межами — 404. Панель «Каталог» у шапці відкривається наведенням миші або кнопкою-стрілкою (Enter/Пробіл, дотик), але не фокусом клавіатури: Tab проходить шапку, а не все дерево; Escape закриває панель і повертає фокус на стрілку. Сторінка знятого з продажу (архівного) варіанта лишається доступною й закритою від індексації, але без тега canonical. Якщо назва чи адреса нової або перейменованої категорії вже є в іншої, адмінка називає ту категорію й що саме збіглося (з 02.11). Категорія з будь-якою кількістю готових SKU публікується однією дією: понад 499 SKU вони вмикаються частинами, а категорія з'являється на сайті останньою, разом з усіма (з 02.11). У Google-фіді товар з одним активним варіантом більше не позначається групою.

**Аудит виконаного обсягу, 31.10.2026 — лише локально, не production:** якщо збереження в новій адмінці відхилено ще до першого запису (наприклад, Prom змінив залишок того самого товару між перевіркою й записом), каталог одразу відкривається знову — раніше вітрина й оформлення замовлення відповідали «каталог оновлюється» до ручного втручання розробника; збереження, перерване після запису (збій процесу), позначається «потребує відновлення», а розробник відкочує або завершує його командою `catalog-recover.cjs` (інструкція — рунбук релізу). Нову категорію не можна назвати адресою сторінки сайту (`checkout`, `catalog`, `faq`…) чи старою адресою іншої категорії, а посадкову сторінку — старою адресою іншої сторінки: інакше старе перенаправлення мовчки переставало працювати. Товар зі списку добірки на головній не видаляється — адмінка пояснює чому (раніше — незрозуміла помилка). Після кожної операції каталогу Google-фід перебудовується одразу, без вікна з відповіддю 503. Посадкові сторінки нової адмінки уточнюють `product_type` у фіді за своїми фільтрами. Перехід із відфільтрованої категорії на відповідну посадкову сторінку зберігає мітки реклами (`gclid`, `utm_*`). Меню великого каталогу повідомляє про завантаження й помилку гілки та дає «Спробувати ще»; сторінки каталогу не падають, якщо каталог змінився між сторінками дерева, і витримують понад 20 000 категорій.

**Великий каталог, 30.10.2026 — лише локально, не production:** для покупця й Merchant нічого не змінилось (ціни, порядок, склад лістингів, sitemap, вміст фіду — побайтово ті самі на стенді); змінились швидкість, пам’ять і форма читань. Google-фід генерується потоково й зберігається стисненим — та сама відповідь `/feeds/google-shopping.xml` (ті самі байти й заголовки); на екрані фіду адмінки «виключено з фіда» рахує всі виключення, а таблиця на великих обсягах показує перші 500 («Показано перші N з M»). Адмінка читає категорії для селектів зі сторінок `GET /categories/options`, а характеристики вибраної категорії — за id; старий `GET /categories` лишається без змін для попереднього фронтенду до R04. Дуже глибокий шлях категорії (понад ~2 000 рівнів із довгими назвами) приходить з позначкою й дочитується посторінково — хлібні крихти й BreadcrumbList повні. Шапка «Каталог» (рішення власника 30.10): поки категорій небагато (до 150 посилань, як зараз) меню в HTML те саме; на великому каталозі в HTML — розділи й їхні підгрупи (до 30 на гілку, далі «Усі (N) →»), глибші рівні розкриваються з підвантаженням у панелі й мобільному меню; плитки підкатегорій на `/catalog` і в групах працюють за будь-якої кількості категорій (раніше понад 100 товарних категорій зникали). На 10 000 категорій / 100 000 товарів: фід при старті + 10 покупців — пік пам’яті 450 MiB, читання каталогу p95 ≤ 0,32 с, сторінки 230–470 КБ; на дереві зі 150 000 категорій усі читання працюють у купі 400 МБ — деталі в [M0 evidence](../plans/plan-0010-m0-evidence.md).

**Каталог-навігатор, 03.11.2026 — лише локально, не production (Plan-0010 P20, рішення власника):** `/catalog` і сторінки груп більше не показують сітку товарів із фільтрами. Сторінка в одну колонку на всю ширину (рішення власника 14.11.2026; ліву колонку з деревом прибрано — вона повторювала плитки й звужувала все нижче): біля заголовка — «Прайс-лист» і «Опт»; плитки категорій із фото розтягуються на всю ширину (одна — рядок, дві — навпіл, більше — рівна сітка), плитка групи називає свої перші підкатегорії одним рядком; «Популярні добірки» — посадкові сторінки пігулками з кількістю товарів, видно всі (посадкові сторінки ніде не показуються як підкатегорії — рішення власника 10.11.2026); далі «Новинки», «Акції» (лише коли є товари на акції; під «Новинками» — рішення власника 11.11.2026) і на `/catalog` — добірки з адмінки «Вітрина». Заголовки сторінки набрано одним шрифтом (Unbounded). Фільтри — лише на сторінці товарної категорії. `?page=N` на навігаторі веде на чисту адресу, інші параметри лістингу — 404. На головній посилання під «Новинки» — «До каталогу».

**Головна під першим рядом, 14.11.2026 — лише локально (рішення власника, [макет](https://claude.ai/artifact/C12tBPY9eZkjGnEnn6WZqh)):** товар не показується на головній двічі — добірка пропускає те, що вже стоїть у «Новинках» або в добірці вище, і показує наступні товари; добірку, де товари обрано вручну, показано як обрано. Кожна добірка — полиця: темна обкладинка з фото, назвою, кількістю товарів і «Дивитися всі» (фото й кількість — з категорії або посадкової сторінки, на яку вказує добірка; у добірки з обраних товарів обкладинка без фото й веде до каталогу) і п'ять карток поруч; на телефоні обкладинка — компактний рядок, під ним чотири картки у два стовпці. Смуга «Прайс-лист» темна, як картка «Купуєте оптом?»; смуга й обкладинки добірок мають живий фон «Аврора», той самий, що в банера: він рухається лише на видимих картках, за «менше руху» — один нерухомий кадр, без WebGL — градієнт тих самих кольорів. Стрілка в «Новинках» показується, лише коли є куди гортати. Перший ряд, шапка й картки товарів без змін; на `/catalog` добірки лишились стрічками.

**Фільтр-діапазон без кнопки «Застосувати», 14.11.2026 — лише локально (рішення власника):** у фільтрах товарної категорії всі зміни застосовуються одразу: галочка — після кліку, повзунок — коли відпущено, числа «від / до», введені руками, — після Enter або коли покупець виходить із цих двох полів (клік деінде, Tab, «Готово» на телефоні). Окремої кнопки немає. Введений діапазон не губиться, якщо одразу після нього поставити галочку в іншому фільтрі.

**Стрічки товарів — картка на товар, 14.11.2026 — лише локально (Plan-0010 P26, рішення власника):** у «Новинках», «Акціях» і добірках (на `/catalog`, сторінках груп і на головній) одна картка відповідає товару, а не кожному кольору: назва товару, кружечки кольорів і «N кольорів», ціна «від N ₴» — найнижча серед варіантів, які можна купити зараз, кнопка «Обрати колір» відкриває сторінку товару. Кольори, яких немає в наявності, лишаються в рядку приглушеними, а коли в наявності лише частина варіантів, картка це пише: «10 кольорів · 1 у наявності». Товар з одним варіантом (або один акційний варіант у «Акціях») показує свою ціну, стару ціну під час акції й «В кошик»; колір — окремим рядком. Якщо варіанти товару — не кольори зі словника (наприклад, номінальний струм), картка пише «N варіантів» і «Обрати варіант»: назву характеристики з адмінки картка у фразу не підставляє, бо її відмінок і множину вивести неможливо. Правило однакове для всіх категорій. Стрічка з одного-двох товарів показує їх широкими картками на всю ширину. Сітка товарів у категорії й пошук не змінились: там одна картка — один варіант. Блок «Популярні види» на сторінці категорії теж став пігулками з кількістю, усі видно одразу.

**Покупецька вітрина нового каталогу, 27.10.2026 — лише локальний стенд, не production:** `/catalog` (весь каталог), сторінки груп і v2 товарних категорій читають `GET /products/catalog/v2` (з 03.11 `/catalog` і групи — навігатор, див. вище); v1 категорія (філамент) лишається на попередній сторінці з кольоровими фільтрами й лендінгами до міграції. Фільтри будуються з налаштувань категорії (список значень із лічильниками, діапазон для чисел, ціна, наявність, підкатегорії/бренд для груп), стан повністю в URL (`f.<key>`, `f.<key>.min/max`, `category`, `brand`, `price.min/max`, `in_stock`, `sort`, `limit`, `page`), значення не розбиваються комами. За SEO-матрицею: невідомі параметри, сторінка поза діапазоном і фільтри без результату — 404; `?page=1` — постійний redirect; фільтри/сортування/порожній розділ — `noindex,follow` без canonical; чистий розділ і `?page=N` — self-canonical. Справжні 404/308 перевірено на production-збірці; для цього прибрано `loading.tsx` у розділах і товарах (раніше production теж віддавав soft-404 з 200), ціна — без skeleton під час переходу. Навігація — публічне дерево довільної глибини без порожніх гілок; мобільне меню розгортає вкладені рівні; крихти: Головна → Каталог → предки → розділ, на товарі — повний шлях із `category_path`. Сторінка товару v2 показує характеристики з визначень (мітки enum, Так/Ні, одиниці), значення осі в назві, бренд лише з brand-сутності, без вигаданого кольору; назва — база → налаштований допис категорії → варіант.

**Міграція філаменту на нову структуру, 27.10.2026 — лише локальний стенд:** категорія «Філамент» переведена на v2 на місці журнальною міграцією: ті самі адреси розділу, товарів і лендінгів, артикули, назви, ціни й залишки. «Виробник» лишився звичайною характеристикою й фільтром (бренд на сторінці й у фіді береться з нього), вага й діаметр — числами з одиницями, колір варіанта — значенням зі словника кольорів (фільтр за родиною зі свотчами, як раніше). 14 лендінгів працюють як закріплені фільтри нової вітрини з власними текстами й FAQ; плитки «Популярні види» на сторінці розділу. Старі адреси фільтрів (`?polymer=PLA`, `?color_family=black`) ведуть одним постійним redirect на нові, а точний збіг із лендінгом — на сам лендінг. Кількість товарів, лічильники фільтрів, лендінги й фід (301 позиція) збігаються зі станом до міграції. Сторінка рефілу зберегла попередження (посилання на варіант із котушкою прибрано 04.11.2026). Прайс-лист читає лише видимі категорії. Обмеження: опубліковані товари поки не редагуються новим редактором (active edits), PDF/partner API/Prom sync ще за старим бар’єром, міграцію на production не запускали.

**Редагування опублікованих товарів, 27.10.2026 — лише локальний стенд:** новий редактор у `/admin/categories` редагує товари опублікованої категорії (зокрема мігрований філамент): назви, опис, фото, ціни/залишки як раніше (ціну й надалі оновлює Prom), характеристики (обов’язкові мають лишатися заповненими), значення варіанта — для кольору вибір зі словника. Статус кожного варіанта — як у попередній адмінці: Активний / Чернетка / Архівний; новий варіант типово «Активний»; архівна сторінка лишається доступною без продажу. Адреси й артикули не змінюються; кеш вітрини й фід оновлюються після збереження.

**Адаптери читання, публікація, checkout і фід, 27.10.2026 — локально:** `/products/by-slug`, legacy `/products/catalog` (лише видима v1 категорія; v2 — 409, прихована/невідома — 404), пошук, лендінги (лише видимі v1), кольори, sitemap (лише видимі непорожні вузли та їхні SKU), checkout (SKU прихованої гілки — `VARIANT_UNAVAILABLE` до будь-якого запису) і Google-фід (лише SKU публічних категорій; v2 без кольору, бренд лише з активної brand-сутності, інакше SKU виключається — виправлено 29–30.10: бренд береться з характеристики «Виробник» або прив’язаної brand-сутності, бренди як сутності прибрано з обсягу) працюють, коли в дереві є v2/чернетки, зі збереженими перевірками revision/epoch/maintenance. Прайс-лист, PDF і partner API ще за старим бар’єром. URL, артикули й ціни не змінюються.

**Публічне читання каталогу, 27.10.2026 — локально:** GET `/categories`, `/categories/slug/:slug`, `/categories/:id` використовують явну public projection v1/v2 з revision, ancestors, typed definitions та SEO. Список лишається масивом товарних категорій; групу можна прочитати за slug/ID. Неактивний предок приховує всю гілку. Додано GET `/products/catalog/v2` із category_id або global scope, page/limit/sort та одним JSON filters. Mongo aggregation рахує SKU, підтримує типізовані attributes, price/stock/category/brand, self-excluding facets та стабільний tie-breaker. Ціни фільтруються за реальною акційною ціною. Чернетки/архівні SKU не потрапляють у список; службові supplier/Prom поля не виходять назовні. Під час mutation/revision drift — 503. Color dictionary adapter, підключення UI, product detail/feed/checkout adapters та публікація ще не завершені; новий read API їх не вмикає.

**Доповнення 27.10.2026 — локальний M2:** після bootstrap каталог відкриває новий редактор також у `/admin/products`, `/admin/products/create` та `/admin/products/:id/edit`. До bootstrap зберігається попередній редактор. У draft v2 товарі можна додати SKU до єдиної осі, архівувати та відновити його в draft; фізичного видалення немає. SKU/slug генерує сервер один раз, архівація зберігає identity/commerce та посилання замовлень. Архівні значення осі залишаються зайнятими, максимум 100 sibling SKU включно з архівом. Усі операції проходять через revision/gate/journal/replay; відкат доданого SKU не повертає лічильник артикулів назад. Active та legacy color-linked товари поки недоступні цьому редактору (закрито 27–29.10 — див. вище).

GET typed-draft повертає `readiness`: незаповнені required характеристики, опис, відсутність draft SKU, невалідні ціни/залишки, відсутні фото; невідома вага — окреме попередження. Це перевірка збережених даних за правилами магазину, не автоматична публікація чи обіцянка SEO-результату. Публічна v2-вітрина та feed ще заблоковані до завершення адаптерів (закрито 27.10 — див. вище).

**Локальні зміни Plan-0010 (27.10.2026, ще не production):** paginated tree/children
reads, категорійні правила відображення характеристик, стабільний slug при rename, назва v2-товару в H1/SEO title/Product JSON-LD — як записана, плюс значення варіанта останнім (категорійний допис `product_name_suffix` прибрано 05.11.2026 за рішенням власника),
універсальні title і HTML-посилання SKU. Внутрішній writer підтримує create/move
і delete/convert невикористаних v2 чернеток із journal/recovery. HTTP create/rename/draft-placement
додано для ADMIN за явним rollout flag (типово вимкнено). Адмінка `/admin/categories`
має дерево довільної глибини, створення груп/товарних чернеток, зміну назви зі
сталим slug, вибір батьківської групи/порядку та перевірку стану операції після
втраченої відповіді. Непідтверджений key/body зберігається у sessionStorage;
автоматичного повтору mutation немає. Active/v1 вузли в новому редакторі read-only.
Попередній редактор доступний лише до bootstrap control. Нові категорії
створюються з порожніми definitions; редактор налаштовує string/number/boolean/enum,
unit/required/filter/spec/order/multiple/semantic/options. Незалежна копія отримує
нові серверні key/option IDs. Збереження draft v2 definitions проходить через gate/
journal; будь-які products/SKU/landings references поки консервативно блокують
руйнівні зміни. Назви/порядок/spec можна змінювати без зміни identity.
ADMIN filter-preview читає typed attributes_v2 + variant_axis/variant_value під
read barrier: OR values, AND keys, inclusive ranges, self-excluding SKU counts.
Повертає counts/facets і максимум 50 прикладів ID; межі preview — 5 000 products /
20 000 active/draft SKU. Непідготовлені дані — 503, не порожній успіх.
У товарній v2 draft категорії додано список по 25 товарів із cursor, прив’язаним
до revision/epoch, та форму характеристик підготовленого товару. Типи полів —
із definitions; порожнє число не стає нулем, false зберігається. Єдина вісь
обирається з single-valued полів; дублікати sibling values відхиляються.
**Правила варіації (рішення власника 06.11.2026, як у Magento/Akeneo — локально):** варіацію будують лише
з обов’язкової характеристики-списку, числа з одиницею, так/ні або кольору (не з вільного тексту);
поки за нею варіюються SKU, обов’язковість не знімається. Колір — завжди колір словника для кожного
SKU, навіть єдиного: текстом у товарі його не записати, тож обов’язковий колір — варіація кожного
товару категорії. Фільтр за кольором вмикається сам (за родиною), галочка «У фільтрах» для кольору
заблокована. Фільтри й лендінги можуть використовувати будь-яку характеристику. У філаменті «Колір»
обов’язковий (міграція).
Назва SKU отримує суфікс із enum label, числа/unit, Так/Ні або тексту.
ADMIN typed-draft GET/PATCH використовують revision barrier/gate/journal та
спільний із деревом sessionStorage pending key/body. Запит без details змінює лише
name/attributes_v2/variant_axis/variant_value: slug/SKU/ціни/залишки/промо/images
не перезаписуються, включно з rollback. Всі SKU мають бути draft, склад SKU
незмінний (1–100); без осі рівно один SKU з null. Legacy/color-linked SKU не
конвертуються автоматично. POST `/products/admin/typed-drafts` створює v2 товар
і 1–100 початкових draft SKU з постачальником, typed values, цінами й залишками.
Форма дозволяє додати/прибрати варіанти до першого збереження. Сервер резервує
артикули й генерує URL один раз із базової назви та варіанта; категорійний SEO-допис
не входить до URL. Idempotency/revision/journal захищають від дублювання.
GET/PATCH typed-draft також підтримує details: опис (очищений HTML + JSON),
фото в заданому порядку, ціни, залишки та вагу збережених SKU. Окремий розділ
форми використовує наявні Quill/upload компоненти. Snapshot token відхиляє
застарілу форму після паралельної зміни commerce/media; journal записує лише
змінені поля. URL/SKU/промо не змінюються. Зміна складу вже збережених SKU, перенесення, color dictionary adapter,
публікація та public storefront ще попереду (закрито 27–29.10 — див. вище).
Legacy HTTP записи categories/products/colors/landings блокуються після явного
bootstrap catalog_control (503); до нього flat active v1 працює як раніше.
GET/HEAD та read-only POST цих контролерів перевіряють стан каталогу до/після
читання, включно з PDF. Частково змінений результат відкидається (503, no-store).
Такий самий HTTP barrier діє для партнерського каталогу/наявності; FeedService
перевіряє стан до/після генерації та stamp кешованого XML перед видачею.
Checkout і admin додавання/збільшення позицій перевіряють snapshot SKU до
side effects; збережені позиції та обробка оплат не блокуються каталогом.
Sitemap читає спільний /catalog/sitemap snapshot (з 29.10 — індекс частин `/catalog/sitemap` і частини
`/catalog/sitemap/part` під однією ревізією); помилки джерела не
перетворюються на порожні arrays, lastModified береться лише з реальних updatedAt. Повна v2 міграція/дерево записів ще не
увімкнені (локально увімкнено й перевірено 27–30.10; production — реліз R02); детальні межі — [план](../plans/plan-0010-general-catalog-and-seo.md).

## 1. Загальний огляд

Fillando — повноцінний e-commerce додаток для продажу витратних матеріалів для 3D-друку (PLA, PETG, ABS, TPU, Nylon). Платформа складається з:

- **Backend API** — NestJS + MongoDB (Mongoose), JWT-аутентифікація, RBAC
- **Frontend** — Next.js 16 App Router, SSR/SSG, Zustand, React Query, React Hook Form + Zod

|-------|------|
| `EMAIL` | Реєстрація та логін через email/пароль |

| `GITHUB` | Визначено в enum, але **не реалізовано** |

## 2. Аутентифікація та авторизація

### 2.1 Реєстрація

| | |
|---|---|
| **Маршрут FE** | `/auth/register` |
| **Endpoint** | `POST /auth/register` |
| **Доступ** | Публічний |

**Поля форми:**

| Поле | Тип | Валідація |
|------|-----|-----------|
| `name` | string | Обов'язкове, мін. 2 символи |
| `email` | string | Обов'язкове, валідний email |
| `password` | string | Обов'язкове, мін. 6 символів (FE) / 8 символів (BE) |
| `confirmPassword` | string | Обов'язкове, має збігатися з `password` |

**Бізнес-логіка:**
- Перевірка унікальності email (409 Conflict якщо зайнятий)
- Хешування пароля через Argon2 + `PASSWORD_PEPPER`
- Створення користувача з роллю `USER`, методом `EMAIL`
- Видача JWT access + refresh токенів (httpOnly cookies)
- Збереження хешованого refresh token в БД з IP/UA трекінгом
- Після успіху: збереження user в Zustand store, мердж гостьового кошика

**Відповідь:** `{ message, user: { id, email, name, role, picture } }`

**Бізнес-логіка:**

## 4. Каталог товарів

### 4.1 Сторінка каталогу

| | |
|---|---|
| **Маршрут FE** | `/{categorySlug}` (напр. `/filament`) |
| **Endpoint** | `GET /products/catalog` |
| **Доступ** | Публічний |

Старі дворівневі URL (`/vytratni-materialy-dlia-3d-druku/filament`) віддають 308-редірект
на плоскі (`/filament`) через `redirects()` у `next.config.ts`.

**Query-параметри:**

| Параметр | Тип | За замовч. | Опис |
|----------|-----|-----------|------|
| `category_id` | string | — | **Обов'язковий**, ObjectId категорії |
| `page` | number | 1 | Номер сторінки (від 1) |
| `limit` | number | 20 | Кількість на сторінку (макс. 100) |
| `price_min` | number | — | Мінімальна ціна |
| `price_max` | number | — | Максимальна ціна |
| `sort` | string | `newest` | `newest` \| `price_asc` \| `price_desc` |
| `color_family` | string | — | Родини кольору через кому (`black,white`) |
| `[attribute_key]` | string | — | Динамічні фільтри за атрибутами (через кому) |

**Приклад:** `?category_id=xxx&vyrobnyk=Sony,LG&price_min=100&price_max=500`

`color_family` — **зарезервований** параметр: колір живе на варіанті, а не в
`product.attributes`, тому він не проходить через динамічні фільтри атрибутів
(інакше запит шукав би неіснуючий атрибут і мовчки нічого не знаходив).

Крім `items`, `pagination`, `price_range` і `filter_options`, відповідь містить
`color_options` — по одному запису на кожну наявну в категорії родину кольору
(`{ family, count, hex_stops }`), з якого вітрина малює swatch-кружечки. Опції
рахуються по всій категорії, тож вибір одного кольору не ховає решту.

**Акції в каталозі ([TD-0012](../designs/TD-0012-variant-promotions.md)):** кожна позиція несе
`price` (регулярна) і трійку `sale_price` / `promo_percent` / `promo_ends_at` (усі `null` поза
активною акцією). Фільтр за ціною, сортування за ціною, межі слайдера й лічильники фасетів
рахуються по **ефективній** ціні (`sale_price ?? price`). Картка показує плашку «−N %» над фото,
закреслену регулярну ціну й акційну (`PriceTag`).

**Бізнес-логіка:**
- Агрегація MongoDB: match (category, status=active, атрибути) → `_effective_price` → фільтр ціни → facet (items + total)
- Атрибутні фільтри: OR всередині одного атрибута, AND між різними
- Фронтенд: бічна панель з фільтрами (слайдер ціни, мультиселекти), пагінація через URL

**Відповідь:**
```json
{
```

### 4.3 Хлібні крихти та SEO

- Видимі хлібні крихти й `BreadcrumbList` (JSON-LD) на каталозі, лендінгу та
  сторінці товару генеруються з **одного** масиву, тож розмітка не може розійтися
  з тим, що бачить відвідувач.
- Новий каталог (з 01.11.2026, лише локально): крихти товару повторюють крихти його категорії — «Головна ›
  Каталог › предки › категорія › товар» (рішення власника 01.11); раніше на сторінці товару не було «Каталог».
- Категорія визначається через `GET /categories/slug/{slug}`.
- Пагінація — це посилання (`<a href>`), а не кнопки: краулер переходить за
  посиланнями і не клікає. Перша сторінка має голу адресу, без `?page=1`.
- **Індексація** (TD-0002 §5.4): `?page=N` індексується і має self-canonical;
  будь-який інший параметр (фільтр, сортування, розмір сторінки) робить сторінку
  `noindex, follow` з канонікалом на список без нього. Комбінація фільтрів, яку
  вже покриває лендінг, віддає канонікал на цей лендінг — збіг має бути точним.
- `ItemList` (JSON-LD) на каталозі; `WebSite` + `SearchAction` на головній;
  `Organization` у кореневому layout.
- Категорії в хедері, мобільному меню й футері приходять із `GET /categories`,
  тож нова категорія одразу є в HTML, який отримує краулер.
- Sitemap містить головну, юридичні сторінки, прайс-лист, категорії,
  **опубліковані лендінги** і товари (лише `active`; архівний товар має сторінку,
  але в sitemap не потрапляє).
- `metadata.verification.google` у кореневому layout читається з
  `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`; тег не рендериться, доки значення порожнє.
- Google Shopping фід, Product JSON-LD і GA4 — §24.

## 6. Кошик

### 6.1 Архітектура

Кошик працює в двох режимах:
- **Гостьовий:** Zustand store, `guestItems` зберігаються в localStorage (`fillando-cart`)
- **Авторизований:** Серверний кошик через API, `items` в Zustand синхронізовані з сервером

Мердж при логіні: `POST /cart/merge` — якщо серверний кошик порожній, гостьові товари переносяться.

### 6.2 UI

- **Бічна панель (CartSidebar)** — відкривається по кліку на іконку кошика в хедері
- Бейдж кількості товарів (максимум "99+")
- Список товарів з зображеннями, назвами, цінами
- Контроли кількості (+/-) для кожного товару
- Кнопка видалення (кошик)
- Загальна сума
- Кнопка "Оформити замовлення"

### 6.3 Endpoints

| Метод | Endpoint | Опис | Доступ |
|-------|----------|------|--------|
| `GET` | `/cart` | Отримати кошик (з перевіркою валідності товарів) | JWT |
| `POST` | `/cart/items` | Додати товар | JWT |
| `PATCH` | `/cart/items/:variantId` | Оновити кількість | JWT |
| `DELETE` | `/cart/items/:variantId` | Видалити товар | JWT |
| `DELETE` | `/cart` | Очистити кошик | JWT |
| `POST` | `/cart/merge` | Мердж гостьового кошика | JWT |

### 6.4 Валідація

- При отриманні кошика: перевірка існування варіантів та наявності на складі
- Видалені/відсутні товари потрапляють у `removed_items`
- Кількість не може перевищувати доступний стік (409 Conflict)
- Мердж: якщо серверний кошик вже має товари — гостьові ігноруються

## 7. Оформлення замовлення (Checkout)

| | |
|---|---|
| **Маршрут FE** | `/checkout` |
| **Endpoint** | `POST /orders` |
| **Доступ** | OptionalJwtAuthGuard (гостьове замовлення підтримується) |

### 7.1 Форма checkout

#### Контактна інформація

| Поле | Валідація |
|------|-----------|
| `customer.name` | Обов'язкове |
| `customer.phone` | Обов'язкове, формат `+380XXXXXXXXX` |
| `customer.email` | Обов'язкове, валідний email |

Для авторизованих користувачів поля заповнюються автоматично з профілю.

#### Метод доставки

| Метод | Додаткові поля |
|-------|---------------|
| `NOVA_POST` | Місто (автокомпліт), «Поштомат чи відділення» (два варіанти), відділення (пошук/вибір) |
| `COURIER` | Місто, вулиця, будинок, квартира (опц.) |
| `PICKUP` | Без додаткових полів |

#### Метод оплати

| Метод | Доступність |
|-------|-------------|
| `IBAN` | Завжди доступний (за замовч.) |
| `CASH` | Тільки при `PICKUP` — правило перевіряє і чекаут, і сервер (`OrderService.ALLOWED_DELIVERY_BY_PAYMENT`, TD-0009) |
| `COD` (Накладний платіж) | Тільки при `NOVA_POST` або `COURIER` — так само на обох боках |
| `LIQPAY` | Доступний, якщо в адмінці є активний LiqPay-провайдер (`GET /payment-providers/active/LIQPAY`) |
| `MONOPAY` | Вимкнено (coming soon) |

**Накладний платіж (`COD`):** доступний лише коли посилку везе Нова Пошта — і на відділення (`NOVA_POST`), і адресною кур'єрською доставкою (`COURIER`); при самовивозі заблокований. Вибір методу відкриває модалку-підтвердження: відправка здійснюється за умови часткової передоплати щонайменше 200 ₴, суму уточнює менеджер по телефону — це гарантія викупу посилки з відділення. Без натискання «Погоджуюсь» метод не обирається (закриття модалки повертає попередній метод). Сума передоплати ніде не зберігається — домовленість відбувається поза системою. Замовлення створюється у `payment_status = PENDING` і лишається таким, доки адмін вручну не поставить `PAID` після перерахунку від Нової Пошти.

**LiqPay (онлайн-оплата карткою):** замовлення створюється у `PENDING`, потім FE отримує підписаний payload через `POST /liqpay/checkout` і авто-сабмітом форми редіректить користувача на хостовану сторінку LiqPay. Підтвердження оплати приходить server-to-server на `POST /liqpay/callback` — саме воно переводить замовлення у `PAID` і надсилає лист. Див. [ADR-0009](../adr/0009-online-payment-liqpay.md), [TD-0001](../designs/TD-0001-liqpay-integration.md).

#### Знижковий купон

| Поле | Валідація |
|------|-----------|
| `coupon_code` | 10 символів, A-Z0-9 |

- Валідація в реальному часі через `POST /discount-coupons/validate`
- Результат: `{ valid: true, coupon: {...} }` або `{ valid: false, reason: "NOT_FOUND" | "INACTIVE" | "EXPIRED" }`
- При валідному купоні: показ % знижки та розраховану суму

#### Коментар

- Опціональне текстове поле

### 7.2 Логіка створення замовлення (Backend)

1. Валідація товарів (існування, ціни)
2. Валідація адреси доставки відповідно до методу та сумісності пари «метод оплати ↔ метод доставки» (`COD` — тільки `NOVA_POST` / `COURIER`)
3. Валідація купона (якщо вказано):
   - Пошук за кодом → перевірка `is_active` та `valid_until`
   - Купон **не складається з акцією — на кожному рядку діє більша зі знижок, обидві від регулярної ціни** (TD-0012, переглянуто власником 2026-10-05). Для рядка: `extra = max(0, list_price × qty × discount_percent / 100 − (list_price − price) × qty)`, `discount_amount = round2(Σ extra)`. Неакційний рядок дає повний відсоток купона; акція −10 % з купоном −15 % дає рівно 15 % від регулярної ціни (купон додає 5 %, яких не дала акція); купон не більший за акцію на цей рядок нічого не додає — рядок лишається за акційною ціною. `items[].price` і `subtotal_price` зберігають акційні ціни, купон лишається знижкою рівня замовлення. Якщо сума = 0 (усі рядки на акції з не меншою знижкою) — `400 COUPON_NOT_APPLICABLE` (одноразовий купон не спалюється на нуль). Чекаут показує те саме превʼю (`couponDiscountAmount` у `price.utils.ts`, дзеркало `coupon-pricing.ts` на BE) і пояснює під полем купона, на які акційні рядки купон діє, а які лишаються за акцією
   - Після створення замовлення: `used_count` купона +1; одноразовий купон (`is_reusable: false`) деактивується, багаторазовий лишається активним
4. Розрахунок: `total_price = subtotal - discount_amount`
5. Генерація `order_number`: `"FO-"` + 7-значний лічильник (напр., `FO-0000001`)
6. Створення snapshot товарів (ціна, назва, SKU на момент замовлення). `items[].price` — ціна, яку платить покупець (акційна, якщо акція діє), `items[].list_price` — регулярна, `items[].promo_percent` — відсоток акції або `null`
7. Відправка email підтвердження (для `IBAN`, `CASH` та `COD` — кожен зі своїм шаблоном). Для `LIQPAY` лист-підтвердження надсилається не одразу, а після успішної оплати (з callback).

### 7.3 Сторінка успіху та стани оплати

| | |
|---|---|
| **Маршрут FE** | `/checkout/success?order=FO-…&payment=…[&token=…]` |

- Номер замовлення
- Інформація про оплату, залежна від методу: `IBAN` — "Реквізити будуть надіслані на email", `CASH` — оплата при отриманні, `COD` — нагадування про часткову передоплату від 200 ₴ і дзвінок менеджера
- Підсумок замовлення (підсумок, знижка, загальна сума)
- Кнопка "Продовжити покупки"
- Кошик очищається після створення замовлення; для LiqPay — **лише після** успішного `POST /liqpay/checkout`, інакше збій ініціалізації лишив би покупця без кошика й без оплати

**LiqPay — сторінка показує результат, а не факт переходу.** LiqPay повертає на `result_url` і при успіху, і при відмові, і при скасуванні, тому сторінка сама з'ясовує стан через публічний `GET /orders/lookup/{orderNumber}?token=` (§8.3), опитуючи його кожні 3 с не довше 60 с:

| Стан `payment_status` | Що бачить покупець |
|---|---|
| `PAID` | «Дякуємо за замовлення!»; саме тут (і лише тут) відправляється Google Ads конверсія |
| `PENDING`, карткової сесії не було (`liqpay_retry_after_seconds: null`) | «Замовлення прийнято — оплату карткою не розпочато»: одразу «Оплатити карткою» і «Обрати інший спосіб оплати», без 60 с очікування — callback-у не буде |
| `PENDING`, сесія була | «Очікуємо підтвердження оплати…» з опитуванням; після 60 с — нейтральна картка «Статус оплати ще не підтверджено…» з кнопкою «Оплатити карткою», яка доки триває 15-хвилинний cooldown сервера вимкнена і показує залишок хвилин (одна жива сесія LiqPay на замовлення — захист від подвійного списання, TD-0009 §5.4.3), і «Обрати інший спосіб оплати» |
| `FAILED` / `VOIDED` | **«Оплата не пройшла»**: банк відхилив платіж, кошти не списано, замовлення збережено. Кнопки «Повторити оплату карткою» (повторний `POST /liqpay/checkout` для того ж замовлення, без створення нового) і — лише коли `can_change_payment_method` — «Обрати інший спосіб оплати»: діалог переводить замовлення на накладний платіж / IBAN / готівку (`PATCH /orders/lookup/{orderNumber}/payment-method?token=`), клієнт і сервіс отримують лист; для `VOIDED` зміна недоступна |
| метод у lookup уже не `LIQPAY` | «Спосіб оплати змінено» з поясненням за методом; тут відправляється Google Ads конверсія (як для офлайн-методів); опитування зупиняється |
| `REFUNDED` | «Кошти повернено» |
| немає `token`, або lookup відповів 404/помилкою | нейтральна картка «Замовлення прийнято — статус оплати ми перевіряємо» |

Токен у `result_url` — це право на читання статусу, не сесія: він ніколи не пишеться в `localStorage`, cookies чи аналітику. Повна машина станів — `fillando-fe/docs/checkout-flow.md` §5.

### 7.4 Помилки оформлення та ліміти

- **Куди йде помилка** (`fillando-fe/docs/checkout-flow.md` §6): помилка купона (`Invalid coupon code`, `Coupon is expired`) — червоним під полем купона з фокусом на ньому **і** тостом; усе інше — лише тостом. Правило: помилка біля поля показується тільки тоді, коли зміна цього поля її виправляє.
- **Клієнтська валідація**: після невдалого сабміту сторінка прокручується до першого невалідного поля (`aria-invalid`), включно з містом і відділенням Нової Пошти, які не мають нативного інпуту.
- **Нестача на складі**: бекенд відповідає `409` з текстом `Only N units available for SKU …`; фронтенд показує його тостом як є. Прив'язка до конкретної позиції кошика й український текст — відкритий пункт трекера (Plan-0005, екран 6).
- **Ліміти запитів** (`@nestjs/throttler`, per IP за хвилину; IP — відвідувача, а не вузла Cloudflare: `CF-Connecting-IP`, якщо запит прийшов з адреси Cloudflare, інакше адреса, яку бачить проксі; Plan-0010 P11, 02.11.2026): `POST /orders` — 10, `POST /liqpay/checkout` — 10 (плюс `409 LIQPAY_SESSION_ACTIVE` на другу сесію в межах 15 хв), `PATCH /orders/lookup/…/payment-method` — 5, `POST /discount-coupons/validate` — 20, `GET /orders/lookup/…` — 30, `POST /auth/login` і `/auth/register` — 10, `POST /auth/refresh` — 30, `GET /products/price-sheet` — 20. Перевищення → `429` із заголовком `Retry-After`; на чекауті це тост «Занадто багато спроб. Зачекайте хвилину і спробуйте ще раз.» Глобального ліміту на публічні GET каталогу немає; SSR-запити фронтенда можуть нести `X-Internal-Token` і не тротляться. Деталі — `fillando-be/src/docs/API_AND_SWAGGER.md` §4a.

callback LiqPay; lookup лише читає його. Деталі — `fillando-be/src/docs/LIQPAY_FLOW.md`.

### 9.2 Деталі та редагування

| Endpoint | Опис |
|----------|------|
| `GET /orders/{id}` | Повні деталі замовлення |
| `PATCH /orders/{id}` | Повне оновлення замовлення |
| `PATCH /orders/{id}/status` | Зміна статусу замовлення — лише дозволені переходи (TD-0011) |
| `PATCH /orders/{id}/payment-status` | Швидка зміна статусу оплати (+ transaction_id) |
| `PATCH /orders/{id}/ttn` | Встановлення ТТН Нової Пошти; відправляє замовлення, що ще не пішло |

**Поточний залишок у картці «Що замовлено»** (18.11.2026, локально, не production): замовлення
нічого не резервує, тож між оформленням і підтвердженням товар може закінчитися. Під кількістю
кожної позиції адмін бачить «Зараз у наявності: N» — залишок SKU в каталозі на момент відкриття
замовлення (`items[].stock_now`, читається наживо, в замовленні не зберігається). Якщо залишку
менше, ніж замовлено, рядок червоний із «не вистачає»; якщо SKU видалено — «Товару вже немає в
каталозі». Покупець цього поля не отримує.

**Статуси замовлення** ([TD-0011](../designs/TD-0011-order-status-flow.md)): статус рухають
факти, вручну адмін лише вирішує.

```
NEW ─► PROCESSING ─► CONFIRMED ─ ТТН ─► SHIPPED ─ НП «отримано» ─► DELIVERED ─ PAID ─► COMPLETED
       (написав     (клієнт                    └ НП відмова ─► RETURNING ─► RETURNED
        клієнту)    підтвердив)
NEW / PROCESSING / CONFIRMED ─► CANCELLED ─ «Відновити» ─► NEW     (самовивіз: «Видано» → DELIVERED)
```

- **Вручну** адмін веде замовлення лише до відправки: «Очікує підтвердження» (`PROCESSING`),
  коли написав клієнту, «Підтверджено», коли клієнт відповів; ці два і «Нове» міняються вільно.
  Далі вручну — «Скасувати», «Видано» (самовивіз), «Доставлено» з «Відправлено» (запасний
  шлях, коли трекер не бачить посилку), «Повертається», «Повернено», «Нове» зі скасованого.
  Плюс `PAID` для накладного платежу, IBAN і готівки. Статус міняється випадаючим списком з
  усіма статусами, де недоступні з поточного — неактивні за `allowed_status_transitions` з
  `GET /orders/{id}`; інший перехід бекенд відхиляє `409 INVALID_STATUS_TRANSITION`
- **ТТН відправляє замовлення:** `PATCH /orders/{id}/ttn` у `NEW`/`PROCESSING`/`CONFIRMED` тим
  самим записом ставить `SHIPPED` — **незалежно від способу доставки**: ТТН на «самовивозі»
  означає, що замовлення все ж відправили (оптовий покупець за рахунком — типовий випадок; у
  проді таких 23 з 39), і далі його веде трекер. Самовивіз без ТТН видається руками
  («Доставлено»). Уже відправлені статус не змінюють. Поки ТТН немає, покупець ще може змінити
  спосіб оплати (TD-0009)
- **`COMPLETED` = доставлено + оплачено** і вручну не ставиться: що з двох настало другим,
  той запис і закриває замовлення (трекер на оплаченому, `PAID` на доставленому). Зняття `PAID`
  повертає `DELIVERED`
- **Відправлене не скасовується** — тільки повертається (`RETURNING → RETURNED`)
- **Історія:** кожна зміна `order_status` і `payment_status` дописується в `status_history`
  (`at`, хто — адмін / покупець / Нова Пошта / LiqPay / система, примітка). Адмінка показує
  картку «Історія статусів»; покупцю історія не віддається
- Запис адмінки умовний на прочитані статуси: якщо трекер чи callback встиг раніше —
  `409 ORDER_STATUS_CHANGED`, сторінка перечитує замовлення
- `PROCESSING` змінив зміст: було «В обробці» (збірка після підтвердження), стало «Очікує
  підтвердження» перед `CONFIRMED`. Старі записи переводить одноразова міграція (поза репо, запуск власником при релізі)
  (з ТТН → `SHIPPED`, без — `CONFIRMED`), відрізняючи їх за відсутністю `status_history`

**Статуси оплати:** `PENDING` → `PAID` / `FAILED` / `REFUNDED` / `VOIDED`

При скасуванні замовлення або поверненні посилки (`RETURNED`) неоплачена оплата (`PENDING`/`FAILED`) автоматично переходить у `VOIDED` («Скасовано»); уже оплачене замовлення лишається `PAID`, і адмін вручну ставить `REFUNDED` після реального повернення коштів. Див. [state-machines](../architecture/state-machines.md#крос-машинне-правило-скасування-або-повернення), [TD-0003](../designs/TD-0003-order-cancellation-payment-status.md), [TD-0011](../designs/TD-0011-order-status-flow.md).

**Накладний платіж в адмінці:** пара «метод оплати ↔ метод доставки» валідується на бекенді при `PATCH /orders/{id}` — 400, якщо `COD` опиняється разом із `PICKUP` (перевіряється ефективна пара, тож помилку дає і зміна лише оплати, і зміна лише доставки). В UI пункт `COD` заблокований, коли обрано самовивіз, а перемикання доставки на `PICKUP` автоматично скидає оплату на `IBAN`. Для `COD` оплату підтверджує сама видача посилки: покупець платить на відділенні, тож коли трекер Нової Пошти бачить «отримано», замовлення тим самим записом стає `PAID` і `COMPLETED` (TD-0011). Адмін може поставити `PAID` і раніше вручну (встановлення ТТН статус оплати не змінює).

**Автоматичне відстеження доставки (Нова Пошта):** щогодини (`order/tracking`, лише
коли `RUN_CRON=true`) бекенд опитує `TrackingDocument.getStatusDocuments` (до 100 ТТН
за запит) для замовлень із ТТН (будь-який спосіб доставки) у статусі `SHIPPED` (а також `NEW` /
`PROCESSING` / `CONFIRMED` — для замовлень, записаних до TD-0011), створених за останні 60 днів.
- Посилку отримано (коди НП `9`, `10`, `11`, `106`): → `DELIVERED`, а оплачене (`PAID`) — одразу
  `COMPLETED`. **Накладний платіж** (`COD`, оплата `PENDING`): покупець заплатив на відділенні, тож
  тим самим записом оплата стає `PAID`, а замовлення — `COMPLETED`; в історії обидві зміни від
  «Нова Пошта». Неоплачене замовлення з іншим способом оплати (IBAN) лишається `DELIVERED` і
  закривається тієї миті, коли адмін ставить `PAID`
- Відмова чи припинення зберігання (коди `102`, `103`, `105`): → `RETURNING` («Повертається»)
  і лист на `SERVICE_EMAIL`. Якщо лист не пішов, статус теж не змінюється — наступний прогін
  повторить обидва
- Видалено / ТТН не знайдено (коди `2`, `3`): лише лист, статус **не** змінюється
- Лист — один раз на код (`nova_post_alerted_code`)
- Інші коди (у дорозі, на відділенні…) — лише записується `nova_post_status`
- Запис умовний на прочитані `order_status`, `payment_status` і ТТН: якщо адмін змінив їх
  під час прогону, перемагає адмін. Нова ТТН (`PATCH /orders/{id}/ttn`) скидає збережений
  статус і позначку листа. Кожна зміна статусу йде в `status_history` з приміткою про код НП
- Статус оплати робот змінює лише для накладного платежу (вище); для IBAN, готівки й LiqPay — ніколи

**Редагування складу замовлення (`PATCH /orders/{id}`, поле `items`):**

- `items` — це **повна заміна** списку товарів: адмін може змінити кількість і **видалити товар**, не передавши його у масиві
- Кожен елемент: `variant_id` (MongoId) + `quantity` (≥ 1); перевіряється наявність варіанта та достатній `stock`
- `subtotal_price` та `total_price` перераховуються сервером; якщо до замовлення застосований купон — `discount_amount` перераховується за тим самим правилом, що й при оформленні (більша зі знижок на кожному новому рядку, див. 7.2), без відмови: якщо купону нема що додати, він дає 0
- Порожній масив `items: []` заборонений (400) — замовлення не може залишитись без товарів
- Ручна знижка (`manual_discount`) зберігається й віднімається після купона: `total_price = subtotal_price − discount_amount − manual_discount.amount`

**Знижка магазину (`PATCH /orders/{id}`, поле `manual_discount`):**

Клієнт після оформлення просить знижку (наприклад, 50 ₴), і адмін фіксує її в замовленні.

- `{ amount, reason }`: `amount` > 0 ₴ (до 2 знаків), `reason` 1–300 символів, обов'язкова; `null` прибирає знижку. Зберігається з `applied_at`
- Додається до купона; більша за суму після купона → `400 MANUAL_DISCOUNT_TOO_LARGE`. Редагування `items` знижку зберігає й перевіряє ту саму межу
- **Лише до оплати:** `payment_status` `PAID` / `REFUNDED` → `409 MANUAL_DISCOUNT_ORDER_PAID`. Знижка після оплати — це часткове повернення, його роблять поза системою
- Поки відкрита LiqPay-сесія (15 хв cooldown), знижку не можна змінити: `409 LIQPAY_SESSION_ACTIVE` + `retry_after_seconds`. Сесію створено зі старою сумою, а callback звіряється з `total_price`
- Покупець (`GET /orders/me*`) бачить лише суму («Знижка магазину»), причину бачить тільки адмін
- Накладений платіж: суму в ТТН адмін виставляє в кабінеті Нової Пошти сам, і там треба вказати новий `total_price`
- UI: `/admin/orders/{id}` → картка «Знижка магазину» (сума, причина, «Застосувати» / «Замінити» / «Прибрати»). Для оплаченого замовлення картка лише для читання
- UI: `/admin/orders/{id}` → блок «Редагування замовлення» → кнопка кошика в рядку товару (локальне видалення, застосовується після «Зберегти зміни»; кнопка заблокована для останнього товару)

### 9.3 Генерація PDF інвойсу

| | |
|---|---|
| **Маршрут FE** | `/admin/orders/{id}` (кнопка в шапці) |
| **Endpoint** | `POST /orders/{id}/invoice` |
| **Доступ** | ADMIN |

**Тіло запиту:**

**Бізнес-логіка:**

### 9.4 Звіт про продажі

Звіт призначений фінансовому відділу й відповідає на питання «що, коли продано
і за скільки» за період. До 21.09.2026 це був набір інвойсів усіх замовлень
періоду, склеєних в один PDF, — те саме питання, поставлене N разів, і жодної
відповіді на це.

| | |
|---|---|
| **Маршрут FE** | `/admin/orders` (кнопка "Звіт" в шапці списку) |
| **Endpoint** | `POST /orders/report` |
| **Доступ** | ADMIN |

**Тіло запиту:**

| Поле | Тип | Валідація |
|------|-----|-----------|
| `date_from` | string (ISO date) | Обов'язкове |
| `date_to` | string (ISO date) | Обов'язкове |
| `order_status` | enum[] | Опціональне — список статусів замовлення, що входять у звіт; відсутнє або порожнє = усі. Одиничний рядок приймається як список з одного елемента |
| `payment_status` | enum[] | Опціональне — список статусів оплати; та сама семантика |

**Формат:** PDF, A4 альбомний, з наскрізним футером і нумерацією сторінок.
HTML → Puppeteer → binary stream. Три розділи:

1. **Продані товари** — агрегація по SKU за весь період: к-сть, у скількох
   замовленнях, сума до знижок, знижка, середня ціна, сума. Середня ціна й сума —
   з урахуванням знижок за промокодами, тож показують, за скільки позиція
   продавалась насправді. Сортування за сумою (після знижок) спадаюче.
2. **Реєстр замовлень** — рядок на замовлення: номер, дата продажу, замовник,
   позицій/одиниць, статус, метод і статус оплати, доставка, ТТН, сума, знижка
   (з кодом купона та позначкою «ручна» для знижки магазину), до сплати. Під рядком — склад замовлення: по рядку на
   позицію «SKU · назва · к-сть × ціна = сума до знижки». ТТН: самовивіз — «—»
   (навіть якщо номер помилково внесено), Нова Пошта / кур'єр без ТТН — «немає».
   Рядок і його позиції не розриваються між сторінками.
3. **Підсумки за період** — до сплати проти оплачено й очікує; розрізи за
   статусом оплати, методом оплати, статусом замовлення, способом доставки;
   продажі за днями.

**Бізнес-логіка:**
- `date_from`/`date_to` — календарні дні в `Europe/Kyiv`, не UTC (`report.period.ts`).
  Наївний `new Date('2026-09-01')` = 03:00 за Києвом і зрізав перші три години
  першого дня періоду
- Дата продажу — `createdAt` (момент оформлення). Поля `paid_at` у схемі немає,
  тож для передоплати дата в звіті ≠ дата надходження коштів; під реєстром про
  це є примітка
- Скасовані / повернені / ті, що повертаються, та відшкодовані замовлення у вибірці рахуються в
  підсумках нарівні з рештою — їх кількість і сума виводяться окремою
  приміткою з вказівкою відняти, якщо звіт іде у виручку
- Знижку замовлення (купон + знижка магазину) рознесено по його позиціях пропорційно вартості рядка
  (`allocateDiscount` у `report.builder.ts`). Купон — це плаский відсоток від
  усього підсумку, тож пропорційна частка дорівнює тій знижці, яку покупець
  отримав на цей рядок; залишок від округлення додається до найбільшого рядка,
  щоб частки сходились у знижку замовлення до копійки. Підсумок колонки «Сума»
  розділу 1 збігається з «До сплати»
- Якщо збережений `subtotal_price` вибірки розходиться з сумою позицій (до
  знижок), з якої рахується розділ 1, — розбіжність друкується явно
- Ліміт: максимум 10 000 замовлень за запит
- Якщо за обраний період немає замовлень — `400 Bad Request`

**UI (фронтенд):**
- Кнопка "Звіт" з іконкою FileSpreadsheet в шапці списку замовлень
- По кліку відкривається Dialog з формою:
  - Дата від / Дата до (нативні `<input type="date">`)
  - Статус замовлення — список чекбоксів з «Обрати все»; за замовчуванням
    відмічено лише «Виконано»
  - Статус оплати — список чекбоксів з «Обрати все»; за замовчуванням
    відмічено лише «Оплачено»
  - Якщо у групі відмічено всі значення, поле в запит не йде (= «усі»); у
    шапці PDF перелічуються обрані статуси або «усі»
- Кнопка "Завантажити" disabled якщо дати не заповнені, `date_from > date_to`
  або в будь-якій групі статусів не відмічено жодного (під групою —
  «Оберіть хоча б один статус»)
- Форма скидається при закритті модалки
- toast success/error для зворотного зв'язку

**Інвойс окремого замовлення** лишається доступним з картки замовлення
(`POST /orders/:id/invoice`, §9.3) — звіт його більше не містить.

### 9.5 Дашборд аналітики замовлень

Відповідає власнику на питання «у які дні тижня й години приходять замовлення і на яку суму» —
за цим виставляється денний бюджет Google Ads. Показує **всі** замовлення магазину (у схемі
немає `utm`/`gclid`), не лише рекламні; про це сказано під заголовком сторінки.

| | |
|---|---|
| **Маршрут FE** | `/admin` (головна адмінки; секції синхронізації НП / Prom лишились нижче) |
| **Endpoint** | `GET /orders/stats?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD` |
| **Доступ** | ADMIN |

**Параметри:** обидві дати — календарні дні в `Europe/Kyiv` (ті самі `storeDayStart`/`storeDayEnd`,
що й у звіті §9.4), опціональні. Без них — останні 30 днів до сьогодні за Києвом; одна дата —
30-денне вікно від неї. `date_from > date_to`, період довший за 366 днів або неіснуючий день —
`400`. Порожній період — **не** помилка: усі структури повертаються з нулями.

**Відповідь** (`OrderStatsResponseDto`):

| Поле | Що це |
|------|-------|
| `period`, `previous_period` | `{ date_from, date_to, days }`; попередній період тієї ж довжини закінчується за день до `date_from` |
| `totals`, `previous_period_totals` | `{ orders, cancelled, paid, revenue, avg_order_value, units }` |
| `by_day[]` | кожен день періоду, нульові включно: `{ day, weekday, orders, cancelled, paid, revenue, units }` |
| `by_weekday[]` | завжди 7 рядків Пн(1)–Нд(7): `{ weekday, days_in_range, orders, revenue, avg_orders, avg_revenue }` |
| `by_hour[]` | 24 рядки, київська година: `{ hour, orders, revenue }` |
| `heatmap[]` | 168 клітинок «день тижня × година»: `{ weekday, hour, orders }` |
| `by_payment_method[]`, `by_delivery_method[]`, `by_order_status[]`, `by_payment_status[]` | усі значення enum, нульові включно, найчисельніші першими: `{ key, orders, revenue }` |
| `top_products_by_revenue[]`, `top_products_by_quantity[]` | до 10: `{ variant_id, product_id, sku, name, quantity, orders, revenue, avg_price }` |

**Визначення:**
- `orders` — усі оформлені в періоді, незалежно від долі.
- `cancelled` («не виручка», спільне правило зі звітом §9.4, `helpers/revenue.helpers.ts`) —
  `order_status` ∈ {CANCELLED, RETURNING, RETURNED} **або** `payment_status` ∈ {VOIDED, REFUNDED}.
  Таке замовлення лишається в `orders`, у `by_hour` і в теплокарті (воно було оформлене — ці
  зрізи відповідають на «коли замовляють»), але дає 0 у `revenue` та `units`.
- `paid` — `payment_status = PAID`, незалежно від `cancelled`: оплачене й потім скасоване
  замовлення — це борг на повернення, і дашборд його не ховає.
- `revenue` — Σ `total_price` не-скасованих (після купона і знижки магазину, без доставки — те,
  що звіт називає «До сплати»). `avg_order_value = revenue / (orders − cancelled)`.
- `by_weekday[].avg_*` ділиться на `days_in_range` — кількість таких днів тижня в періоді
  **включно з днями без замовлень** (2 у 14-денному вікні, 4–5 у 30-денному); рахується з
  `by_day`, а не із замовлень, тож порожній понеділок — усе одно понеділок.
- Топ товарів — вартість рядків (`price × quantity`) не-скасованих замовлень **до купона**, як у
  таблиці товарів звіту; тому сума топу не збігається з `totals.revenue`. Ключ — `variant_id`
  (запасний — SKU); `name` береться з найновішого замовлення.
- Дата продажу — `createdAt` (момент оформлення), не дата оплати: `paid_at` у схемі немає.

**Реалізація (BE):** `OrderService.getStats` → два паралельні вузькі запити
`OrderRepository.findStatsSource` (лише потрібні колонки, без покупця/адреси/історії, новіші першими,
кап 20 000 з попередженням у лог) → чистий `stats/stats.builder.ts` (тести за зразком
`report.builder.spec.ts`, включно з DST-днем 25.10). Колекція `orders` отримала індекс
`createdAt: -1`. Маршрут оголошений до `/:id`, інакше «stats» читається як id замовлення
(закріплено RBAC-тестом). Ескейп на майбутнє — `$facet` із `$dateToParts` у `Europe/Kyiv` —
описано в `fillando-be/src/docs/ORDER_ADMIN_API.md`.

**UI (FE, `admin/analytics/`):**
- Рядок періоду: пресети «7 / 14 / 30 / 90 днів», «Цей місяць», «Минулий місяць» + довільні
  «Від / До» (`<input type="date">`, `max` = сьогодні за Києвом). Період живе в URL
  (`?from=&to=`); дефолтний період адресу не змінює; обернена пара пояснюється підказкою, а
  не мовчки міняється місцями.
- Під пікером — рядок періоду, «порівняно з попереднім періодом такої ж довжини (…)» та примітка
  «дата — момент оформлення; усі замовлення магазину, не лише з реклами».
- **Порядок блоків** (власник, 2026-10-16: «важливо бачити, коли замовлення надходять»):
  спершу три блоки часу — замовлення по днях, профіль тижня, теплокарта; KPI, розрізи й топ
  товарів — у згорнутому `<details>` «Підсумки, розрізи й топ товарів» нижче.
- **Замовлення по днях** — стовпчики: оформлені (зелені) і скасовані (сірі, поруч, не стек);
  межі тижнів видно без лічби (власник, 2026-10-16): підписи осі лише на понеділках («Пн 13 жовт.»;
  при менш ніж двох понеділках — щодня), тонка лінія на кожному понеділку, субота–неділя
  затінені, у підказці — день тижня («понеділок, 13.10.2026»), у таблиці — колонка «День»;
  перемикач «Лише оплачені» міняє основну серію на `paid`; виручка по днях — окремий малий графік
  під ним на тій самій осі X (не друга вісь); `<details>` «Таблиця по днях».
- **Профіль тижня** — ключовий блок: речення «Найсильніший день — …: у середньому N замовлень і
  S ₴ на день. Найслабший — …» (за `avg_orders`, нічия — за `avg_revenue`; «Недостатньо даних»,
  коли все 0) + два малі графіки Пн–Нд (замовлень на день, виручка на день), найкращий день
  темнішим, + таблиця з `days_in_range`.
- **Коли замовляють** — теплокарта 7 × 24 (CSS-сітка, один відтінок у 5 сходинок), кожна клітинка
  з `aria-label` «Пн, 09:00 — 3 замовлення», підпис «київський час».
- **KPI** (5 плиток, спільна `KpiTile` з Google Feed): замовлень, виручка, середній чек, частка
  оплачених, скасовано — кожна з дельтою до попереднього періоду; дельта частки оплачених — у
  **п.п.**; «—», коли попередній період порожній.
- **Розрізи** — спосіб оплати, доставка, статус замовлення, статус оплати: підпис із
  `*_LABELS` (невідомий ключ — як є), смужка частки, `orders · % · revenue`.
- **Топ товарів** — перемикач «За виручкою / За кількістю», посилання на картку товару лише коли
  `product_id` не `null`.
- Стани: скелетон на першому завантаженні (і як fallback `Suspense`), «Не вдалося завантажити
  аналітику» + «Спробувати знову», «За обраний період замовлень немає» (пікер лишається); при
  рефетчі попередні цифри лишаються на екрані приглушеними (`keepPreviousData`).
- `recharts` 3.x імпортується лише з `admin/analytics/` і потрапляє тільки в чанк `/admin`.

**Обмеження для рішень про бюджет:** профіль тижня за 30 днів спирається на 4–5 днів кожного
типу — один великий оптовик робить вівторок «найсильнішим»; для бюджету дивитись 90 днів, 30 —
для останніх тенденцій. Дашборд не знає, звідки прийшов покупець (немає `utm`/`gclid`), тож
«у понеділок більше замовлень» ≠ «у понеділок реклама працює краще».

- `slug`: генерується з назви товару + v_value (напр. `futbolka-bazova-chorna`). Назви товарів після міграції 3k — короткі («Kingroon PLA Silk Rainbow», історичний словник коротких назв, TD-0002 §5.2.4); у локальній реалізації Plan-0010 перейменування товару/варіанта зберігає slug; явна зміна адреси з redirects ще розробляється
- `name` варіанту: `"{назва товару} — {v_value}"`

**Валідація перед створенням:** `POST /products/validate` — перевірка унікальності slugs та SKUs

| | |
|---|---|

**Endpoints:**

| Метод | Endpoint | Опис |
|-------|----------|------|
| `GET` | `/products/{id}` | Отримати товар |
| `PATCH` | `/products/{id}` | Оновити метадані товару |
| `GET` | `/products/{id}/variants` | Всі варіанти |
| `POST` | `/products/{id}/variants` | Додати варіант |
| `PATCH` | `/products/{id}/variants/{variantId}` | Оновити варіант |
| `DELETE` | `/products/{id}/variants/{variantId}` | Видалити варіант |
| `PATCH` | `/products/{id}/variants/{variantId}/images` | Замінити зображення варіанту |
| `PATCH` | `/products/{id}/promotion` | Акція на всі варіанти: `{ promo_percent, promo_ends_at? }` або `{ promo_percent: null }` (TD-0012) |
| `DELETE` | `/products/{id}` | Видалити товар (з усіма варіантами) |

**Акція ([TD-0012](../designs/TD-0012-variant-promotions.md)):** картка «Акція» на сторінці
редагування ставить або прибирає відсоток (1–90) і необов'язкову дату «до» на всі варіанти
товару одним запитом; у модалці варіанта ті самі два поля для одного варіанта (порожній відсоток =
акції немає; дата без відсотка ігнорується). Таблиця варіантів показує закреслену регулярну ціну,
акційну й плашку «−N %». Адмінські відповіді варіантів несуть `supplier_price` (що магазин платить
постачальнику); якщо акційна ціна нижча — амбер-попередження з переліком SKU, збереження не
блокується. Акційна ціна **не зберігається** — виводиться з відсотка при кожному читанні, тож
Prom-синк, який перезаписує `price`, її не зачіпає. Запис акції одразу оновлює вітрину і
перегенеровує Google-фід; акція, що закінчилася за датою, підхоплюється кроном раз на 10 хв. Налаштований непрострочений відсоток зберігається в модалці навіть за нульової ціни або округлення без економії — зміна ціни може зробити акцію активною. Прострочену акцію в поля не підставляють.

| | |
|---|---|

| **Endpoint** | `POST /products/price-list/pdf` |
| **Доступ** | ADMIN |

**Тіло запиту:**

| Поле | Тип | Валідація |
|------|-----|-----------|
| `category_ids` | string[] (mongo id, max 200) | Опціональне — відсутнє або порожнє означає всі категорії |
| `in_stock_only` | boolean | Опціональне, default `false`. Має бути справжній boolean (`"true"` відхиляється) |
| `orientation` | enum `portrait` \| `landscape` | Опціональне, default `portrait` (вікно адмінки надсилає `landscape`) |

**Формат (рішення власника 06.11.2026 — локально):** витяг наявності без оптових знижок («знижку буду
сам людині говорити»): колонок «Ціна від 50кг / від 100кг» і полів `tier1_percent`/`tier2_percent` більше
немає (старий клієнт, що їх надсилає, отримує той самий PDF — зайві поля відкидаються). PDF A4,
HTML → Puppeteer → binary stream. **Окрема таблиця на кожну категорію** (назва категорії — заголовок,
порядок — як у каталозі): `SKU`, `Назва` (**об'єднана вертикально** на всі варіації товару), колонки
категорії — характеристики, за якими її фільтрує каталог, і колір (значення з одиницями й підписами:
«1.75 мм», «Шовковий (Silk)»; значення товару об'єднані на його варіації, колір — у кожному рядку),
`Варіант` (лише коли варіацію не показує жодна колонка: стара категорія, вісь не є фільтром), `К-ть`,
`Ціна`. Ширина колонок — за вмістом; у книжковій орієнтації дев'ять колонок філаменту тісні, тому вікно
адмінки за замовчуванням — альбомна. Шапка: лого + дата генерації + рядок фільтрів; футер: нумерація
сторінок; заголовок таблиці повторюється на кожній сторінці.

**Бізнес-логіка:**
- Тільки варіанти зі `status = active`; `draft` та `archived` не потрапляють ніколи
- Ціна — звичайна (`price`), без акції й без оптових знижок
- Сортування в категорії: бренд → назва товару → варіант. Бренд у v2 — бренд товару або характеристика
  з позначкою «Бренд», у v1 — атрибут `Виробник`/`Бренд`; товари без бренду йдуть в кінець. uk-UA (`Intl.Collator`)
- Група товару ріжеться на блоки ≤16 рядків, щоб об'єднана клітинка не перетинала розрив сторінки
  (обмеження Chromium). Блоки після першого позначені `(продовження)`
- Порожня вибірка → `400`; понад 20 000 позицій → `400`; паралельна генерація → `409`

**UI (фронтенд):**
- Кнопка "Прайс-лист" з іконкою FileDown в шапці списку товарів
- По кліку відкривається Dialog з формою:
  - Список категорій чекбоксами з майстер-рядком "Всі категорії"
  - Чекбокс "Тільки в наявності"
  - Select орієнтації сторінки: "Вертикальна (книжкова)" / "Горизонтальна (альбомна)", за замовчуванням альбомна
- Форма скидається у дефолти при закритті модалки
- toast success/error для зворотного зв'язку

Деталі реалізації — `fillando-be/src/docs/PRICE_LIST_PDF.md`.

щоб збережений текст був видимий на наступному запиті. Виклик fire-and-forget: збереження не падає.
Невдалий виклик не губиться — він чекає в черзі бекенду (`storefront_purges`) до відповіді 2xx, з повтором і
попередженням у лозі; підтверджене очищення повторюється раз через 10 с (Plan-0010 P12/P15, 02.11.2026). Контракт — `fillando-be/src/docs/STOREFRONT_REVALIDATION.md`,
`fillando-fe/docs/cache-revalidation.md`.

**Одноразові vs багаторазові купони:**
- Одноразовий (`is_reusable: false`, дефолт) — після першого застосованого замовлення купон автоматично деактивується (`is_active: false`)
- Багаторазовий (`is_reusable: true`) — лишається активним після замовлень; діє до `valid_until` або ручної деактивації адміном
- В адмінці тип задається перемикачем «Багаторазовий купон» при створенні/редагуванні; у списку показується тип і кількість використань

**Провайдер:** Resend API

2. **Сервіс** (`SERVICE_EMAIL`) — тема: `"Нове замовлення {orderNumber}"`, `Тип оплати: Накладний платіж`

**Дані листа:** те саме, що й у 17.1, плюс виділений блок про часткову передоплату (щонайменше 200 ₴) і про те, що менеджер зв'яжеться й уточнить суму.

## 24. Google Merchant: фід і structured data

Джерело дизайну — [TD-0006](../designs/TD-0006-google-merchant-feed-and-structured-data.md),
реалізація — [Plan-0006](../plans/plan-0006-google-merchant.md).

Стан на 2026-09-22 (перевірено на проді, не зі статусу плану):

- **фід у проді** — `https://api.fillando.com/feeds/google-shopping.xml` віддає 301 позицію,
  `google_product_category = 499682` на всіх, `lastBuildDate` рухається щогодини;
- **Merchant Center читає саме його** — назви позицій у звіті Google Ads збігаються з `title`
  фіда символ у символ;
- **GA4 не підключений**: у прод-білді фронту `NEXT_PUBLIC_GOOGLE_ANALYTICS_ID` порожній, тож
  усі події §24.3 — no-op. Це блокує аудиторії ремаркетингу й сигнали для PMax;
- **Search Console** не верифікований meta-тегом (`NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION` теж
  порожній); верифікація через DNS або файл із коду не видна.

### 24.1 Google Shopping фід

| | |
|---|---|
| **Endpoint** | `GET /feeds/google-shopping.xml` — публічний, реєструється в Merchant Center |
| **Адмін** | `POST /feeds/google-shopping/regenerate`, `GET /feeds/google-shopping/status` (ADMIN) |
| **Формат** | RSS 2.0 з `g:`-атрибутами (той самий читають Bing і Meta) |
| **Оновлення** | генерація при старті процесу та щогодини (`RUN_CRON`); XML в пам'яті |
| **Холодний старт** | до першої генерації — `503` + `Retry-After: 60`, ніколи не порожній канал |

Позиції — лише `active` варіанти. Поля: `g:id` (SKU), `g:item_group_id` (товар; з 31.10, лише локально — тільки якщо в товару більше одного активного варіанта), `title`
(складається — див. нижче), `description` (текст без розмітки, ≤5000), `link`, `g:image_link` + до
10 `g:additional_image_link` (оригінальні URL — ті самі, що в JSON-LD), `g:availability`
(`in_stock` / `out_of_stock`), `g:price` (UAH, регулярна), при активній акції `g:sale_price` і — за наявності дати — `g:sale_price_effective_date` (`<генерація>/<promo_ends_at>`, TD-0012), `g:brand` (атрибут «Виробник»),
`g:google_product_category` (з категорії), `g:product_type` («Категорія > H1 лендінга» для
найспецифічнішого опублікованого лендінга, інакше назва категорії), `g:condition new`,
`g:identifier_exists false`, `g:color` (словник), `g:material` (v2 — характеристика з позначкою
«Матеріал», у філаменту «Тип пластику»), `g:shipping_weight`,
`g:product_highlight` (v2 — характеристики з таблиці сторінки товару в її порядку, без бренду й
кольору; v1 до міграції — діаметр, вага, `polymer`, `finish`, `reinforcement`, `series`,
`spool_included`), `g:brand` (v2 — бренд товару або характеристика з позначкою «Бренд»),
`g:custom_label_0..4` (тип філаменту · виробник · глибина залишку · ціновий діапазон · швидкість
продажів за 90 днів PAID-замовлень). **Маржі й supplier-полів у фіді немає.**

**`title` = назва SKU, як на сайті** (рішення власника 05.11.2026, локально): «Kingroon PETG (CoPET) 3 кг —
Філамент (пластик для 3D-друку) — Чорний (Black)». Слова для пошуку живуть у самій назві: міграція
каталогу один раз дописує «Філамент (пластик для 3D-друку)» до назви кожного товару й варіації філаменту
перед значенням варіації. Складений заголовок 22.09.2026 (`{Категорія} {тип} {бренд} {діаметр} {вага} —
{колір}`) прибрано — це було правило філаменту для всіх категорій; на проді він діє до релізу.

**`custom_label_0` — сімейство**: `basic` (звичайні PLA/PETG) · `decorative` (є `finish`) ·
`engineering` (є `reinforcement`, або `polymer` ∈ ABS, ASA, PA*, PC, PET, PPA, PPS) · `flex` (TPU).
Раніше там лежала назва категорії — одне й те саме слово на всіх позиціях, поки магазин продає одну
категорію, тож Shopping не мав за чим сегментувати. Після першого фетчу нового фіда групу товарів,
розбиту за старим значенням, треба перерозбити за сімействами.

Виключення (позиції немає): без фото, без ціни, без атрибута «Виробник», зникли товар або
категорія. Попередження (позиція є, лістинг гірший): немає `google_product_category`, опису,
ваги, обов'язкового атрибута категорії. Підсумок генерації бачить адмін на `/admin/feed`.
Деталі — `fillando-be/src/docs/MERCHANT_FEED.md`.

### 24.3 GA4 і Google Ads

**Consent Mode v2 і дані для Google Ads (17.11.2026 — лише локально, не в проді):**

- **Тег завантажується всім відвідувачам.** До відповіді в банері й після «Лише необхідні» всі
  чотири сигнали згоди — `denied`: тег не пише й не читає cookie і надсилає знеособлені сигнали
  (перегляд, покупка з номером і сумою замовлення). Після «Прийняти» — `granted`.
- **Розширені конверсії.** Для покупця, що дав згоду, сторінка «Дякуємо» передає тегу e-mail і
  телефон із замовлення; тег хешує їх у браузері. Потребує перемикача «Allow user-provided data»
  в налаштуваннях тега в акаунті Google Ads — без нього тег ці дані не надсилає.
- **Дані в замовленні** (`orders.attribution`): відповідь у банері завжди; ідентифікатор
  рекламного кліку (`gclid` / `gbraid` / `wbraid`), IP-адреса й тип браузера — **лише за згоди**.
  Ідентифікатор кліку вітрина тримає 90 днів. Покупцеві ці поля не повертаються, в адмінці їх
  віддає лише деталь замовлення. Серверного завантаження конверсій у Google ще немає.
- **Відкликання згоди** стирає ідентифікатор кліку й усе, що зберіг тег (cookie `_gcl_*` / `_ga*`,
  запис `_gcl_ls`).
- Текст банера й політика конфіденційності (§3, §4, §7) описують саме цю поведінку.
- На локальному стенді (`localhost`) бібліотека тега не завантажується: ідентифікатор тега
  за замовчуванням — робочий акаунт Ads, і тестові замовлення не мають у нього потрапляти.

GA4 їде тим самим тегом
другим `config`, коли задано `NEXT_PUBLIC_GOOGLE_ANALYTICS_ID`. Події через `common/lib/ga4-events.ts`
(над чергою `gtag()`): `view_item`, `add_to_cart`, `begin_checkout` (раз за візит чекауту),
`purchase` (агреговано, на сторінці успіху разом з Ads-конверсією). Усі — no-op без id property.
**GA4 `purchase` не імпортується в Ads як конверсія** — Ads-піксель лишається єдиним джерелом
для ставок, інакше кожне замовлення рахується двічі.

## 25. Партнерський API каталогу та наявності (локальна реалізація, деплой очікується)

- `POST /partner/v1/categories`: плоский список категорій, parent_id=null,
  кількість активних доступних артикулів, включно з порожніми категоріями.
- `POST /partner/v1/products/skus`: category_id, cursor і limit у JSON-тілі;
  лише JSON body. Фільтр category_id або весь каталог,
  курсорна пагінація по SKU, limit 1–100; `{items, next_cursor}`.
- `POST /partner/v1/products/lookup`: картки до 100 артикулів, `{items, not_found}`;
  назва, HTML-опис, категорія, характеристики, варіант, фото, URL, вага та наявність.
  Роздрібна ціна `price` у гривнях, `sale_price` (акційна, якщо акція магазину зараз діє, інакше `null`; TD-0012) та `currency: UAH`; без даних постачальника. Критерії доступності однакові з лічильниками й SKU.

- `POST /partner/v1/products/availability` — пакет із 1–100 артикулів;
  `{items, not_found}`, повтори об’єднуються, порядок першої появи зберігається.
  Активні товари з нульовим залишком — в items, невідомі й неактивні — в not_found.
  Валідний пакет завжди 200; ліміт запитів спільний із GET.

- `GET /partner/v1/products/:sku/availability` — точний внутрішній артикул,
  лише активні варіанти; `sku`, `in_stock`, `quantity`, `stock_updated_at`.
- Bearer API-токени, SHA-256 у базі, відкликання з наступного запиту.
- Адмінка `/admin/api-tokens`: створення з назвою партнера, одноразовий показ
  і копіювання, список з датою використання, відкликання з підтвердженням.
- Публічний Swagger `/partner-docs` та `/partner-openapi.json` містять лише
  партнерський контракт. Адмінські операції захищені JWT + ADMIN.
- Ліміт 60/хв/токен, додатково 300/хв/IP; 429 + Retry-After, один процес.
- Деталі: [TD-0010](../designs/TD-0010-partner-stock-api.md),
  `fillando-be/src/docs/PARTNER_API.md`.

- Rate limiting: `@nestjs/throttler` без глобального guard'а; ліміти по ендпоінтах (§7.4), `429` + `Retry-After`, обхід для SSR через `X-Internal-Token`
- Публічні проєкції каталогу — явні allowlist'и (`PUBLIC_VARIANT_FIELDS`, `PRICE_SHEET_PUBLIC_PROJECTION`, фід): `prom_*` і `vendor_product_sku` ніколи не публічні; write-ендпоінти каталогу, вендорів і завантажень — лише `Role.ADMIN` (Plan-0003)
- Паролі: Argon2 + pepper (мін. 16 символів)
- JWT: httpOnly cookies, sameSite, окремі секрети для access/refresh
- Refresh token rotation (видалення старого при кожному оновленні)
- IP/UA трекінг для refresh токенів
- CORS: whitelist за FRONTEND_URL
- RBAC: `@Roles()` декоратор + `RolesGuard`
- Валідація: class-validator (BE), Zod (FE + response validation)
- Whitelist: невідомі поля відкидаються (ValidationPipe)

### Стейт-менеджмент (FE)
- **Zustand** `useAuthStore` — user, isAuthChecked; persist → localStorage
- **Zustand** `useCartStore` — items (сервер), guestItems (localStorage), isOpen
- **React Query** — серверний стейт для каталогу, замовлень, адмін-даних

### HTTP Service (FE)
- Axios singleton з credentials: true
- Автоматичний refresh при 401 (з дедуплікацією)
- Опціональна Zod-валідація response
- Toast-сповіщення при помилках
