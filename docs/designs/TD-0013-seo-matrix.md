# TD-0013 — SEO-матриця та модель варіантів

- **Date:** 2026-10-23
- **Status:** рішення для реалізації D03/D04, затверджене разом із TD-0013 (Approved, 2026-10-31; рішення власника 31.10 внесено); не опис поточного production
- **Related:** [TD-0013](TD-0013-general-catalog-and-seo.md), [Plan-0010](../plans/plan-0010-general-catalog-and-seo.md)

## 1. Обрана модель

Залишаємо багатосторінкові варіанти: кожен активний SKU має стабільний URL,
правильний вибір для кошика, фото, ціну, залишок, власний H1 і self-canonical.
Це наше рішення на основі явно підтримуваної Google multi-page моделі, а не
вимога робити так усім магазинам. Групу не канонікалізуємо на довільний перший SKU.

На сторінці повторюється самодостатній `ProductGroup` зі стабільним
`productGroupID`, повним `Product` поточного SKU і URL-посиланнями на інші
публічні варіанти. `ProductGroup.url` для цієї моделі не додаємо. Розмітка
надходить у серверному HTML. Для одного SKU без осі — звичайний `Product`.

`variesBy` використовує підтримувану семантику color/size/material/pattern/
suggestedAge/suggestedGender. Довжина може бути size лише за змістом даних;
струм не маскується під size/color. Для нестандартної осі публікуємо коректний
`Product` з `additionalProperty`, без обіцянки variant rich results.
[Джерело: Product variants, multi-page та Technical guidelines](https://developers.google.com/search/docs/appearance/structured-data/product-variants).

> **Реалізовано локально (28.10, F09):** `buildProductJsonLd` (FE) — `ProductGroup` для осі кольору
> (v1 і v2 `semantic: color`), розміру й матеріалу; `generic` — Product з `additionalProperty`;
> один SKU — Product. Семантика осі й `semantic_values` приходять із BE; `material` — спільне з
> фідом правило. Live-перевірка — R03.

Самостійно вигаданий GTIN, бренд, рейтинг, відгуки чи властивість заборонені.
Відомі властивості повинні збігатися з видимою сторінкою. Правило self-canonical
не означає гарантії, що Google вибере саме цю canonical або індексуватиме кожен SKU.

## 2. Матриця HTTP-сторінок

`self` — нормалізований абсолютний HTTPS URL. Усі index-сторінки доступні
Googlebot; це не гарантія їх включення в індекс. У sitemap — тільки 200 index
canonical-сторінки, без redirect/draft/службових параметрів. Пагінація доступна
через HTML-посилання; в sitemap достатньо основних listings і всіх товарів.
Форма (29.10.2026, B05/F10): поки набір вміщується в один файл — `/sitemap.xml` і є
цим файлом; понад це `/sitemap.xml` — [sitemap index](https://developers.google.com/search/docs/crawling-indexing/sitemaps/large-sitemaps)
файлів `/sitemap/<n>.xml`, кожен < 50 000 URL (Google: ≤ 50 000 URL і ≤ 50 МБ на файл),
усі з однієї ревізії каталогу; robots.txt указує на `/sitemap.xml`. Склад і правила вище не змінюються.

[Google pagination](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading);
нормалізація/стабільні URL та href — на
[URL guidance](https://developers.google.com/search/docs/specialty/ecommerce/designing-a-url-structure-for-ecommerce-sites).
Єдиний автор policy-функції використовується SSR metadata, sitemap та route handlers.

## 3. Обхід фільтрів: два кроки

На першому релізі filter/sort URL доступні для читання noindex. Не ставити на них
одночасно robots disallow: робот не прочитає директиву. Не створювати HTML-граф
усіх комбінацій: форми підбору окремо, редакторські лендінги — звичайні href.

Після перевірки фактичного індексу та логів можна окремим контрольованим релізом
закрити від обходу тільки простір filter/sort, зберігши доступ до пагінації,
лендінгів і рекламних SKU. Потрібні конкретні URL-тести правил robots; wildcard
для всіх `?` неприпустимий. У M0 без Search Console автоматично цей крок не вмикаємо.
Нульові фасетні результати й неіснуюча пагінація повертають 404.
[Джерело: Faceted navigation](https://developers.google.com/crawling/docs/faceted-navigation).

## 4. Merchant не підміняє canonical сайту

- `id` = наявний SKU, `link` = URL саме цього SKU, без tracking-параметрів.
- Груповий ID зберігається (`product_id`); для одиночного товару без варіативності
  не відправляємо `item_group_id` (реалізовано 31.10, рішення власника: «одиночний» = рівно один
  активний варіант; з другим активним ID повертається автоматично). Заголовок групи спільний, значення осі явне.
- Поточна документація Merchant містить `variant_option` та `item_group_title`:
  перед B10 перевірити їх XML-формат на прикладі фіда. Не покладатися на старе
  припущення, що Merchant підтримує лише колір/розмір. Стандартні поля color/size
  тощо залишаються, коли застосовні.
- Optional `canonical_link` **не відправляємо** у вибраній multi-page моделі;
  canonical задається в HTML. Не вигадуємо неіснуючу базову сторінку групи і
  не відправляємо суперечливі canonical-сигнали.

Джерела: [item_group_id](https://support.google.com/merchants/answer/6324507),
[variant_option](https://support.google.com/merchants/answer/17085214),
[canonical_link](https://support.google.com/merchants/answer/9340054).

## 5. Контрольні приклади й межі підтвердження

1. Чорний/білий філамент: два SKU URL, кожен self-canonical, одна група з color.
2. Ковдра 160×120/180×130: розмір у name/size, не color; дві сторінки, одна група.
3. AVR 40/63 А: різні SKU зі струмом у additionalProperty; не фальсифікувати
   підтримувану вісь structured data. Merchant-option та eligibility перевіряються окремо.
4. Товар без варіантів: Product без порожньої ProductGroup, без групового ID у фіді.
5. `page=2&utm_source=x`: canonical page=2, не page=1; tracking не змінює вибірку.
6. `polymer=PLA&page=2`: redirect на `/filament/pla?page=2` лише якщо існує
   відповідний опублікований лендінг, page існує та набір фільтрів точно збігається.

D03/D04 закриті як дизайн-рішення. Це не live-перевірка Rich Results Test або
Merchant diagnostics; вони входять у F09/B10/R03.

**Реалізація (28.10, F09/F10; аудит 31.10):** «301/308» — постійне перенаправлення: вітрина
віддає 308 (`permanentRedirect` Next), BE `GET /routes/resolve` повертає `status: 301` у тілі; для
Google обидва — постійні. Адреси реалізовано без префікса `/catalog/` (TD-0013 §4.4). Аудит 31.10:
редирект точного збігу з лендінгом тепер зберігає атрибуцію й не спрацьовує для сторінки поза
межами (404 на запитаному URL). Рішення власника 31.10.2026 внесено в рядки «Старий URL» (query не зберігається), «Архівний SKU» (без canonical),
перехідне правило пагінації й §4 (`item_group_id`). Відхилення, знайдені аудитом 31.10, виправлено 02.11 (передрелізні
виправлення, Plan-0010 §8): опублікований лендінг без активних SKU не потрапляє в sitemap і не має плитки на сторінці
категорії (P02, рядок «Відомі порожні»); стара адреса перенесеної категорії — один hop і з фільтром, що збігається з
лендінгом (P03, рядок «Старий URL»).
