# TD-0010 — Партнерський API наявності

Status: Implemented locally (2026-09-12); deployment pending.

Поточний запит власника звужує перший етап TD-0007 до читання каталогу та наявності
за внутрішнім артикулом та керування токенами в адмінці. Дилерські ціни,
замовлення й окрема сутність дилера залишаються поза цим етапом.

- `GET /partner/v1/products/:sku/availability`: точний артикул, лише active-варіанти.
- `POST /partner/v1/products/availability`: 1–100 SKU одним запитом до бази;
  `{items, not_found}`, повтори об’єднуються, порядок першої появи зберігається.
  Невідомі й неактивні — у not_found; валідний пакет завжди 200.
- Контракт: `sku`, `in_stock`, `quantity`, `stock_updated_at` (nullable ISO UTC).
  Для GET невідомий або неактивний артикул → 404; нульовий залишок → 200 із quantity=0.
- `Authorization: Bearer flnd_live_…`: 32 random bytes; у MongoDB лише SHA-256.
- Нова колекція `partner_api_tokens`: назва, префікс, хеш, автор створення,
  дата створення, дата відкликання та останнього використання.
- JWT + ADMIN для створення, списку та відкликання `/admin/api-tokens`.
  Секрет повертається один раз; metadata ніколи не містить хешу.
- Партнерський токен не створює `req.user` і не дає доступу до адмінських API.
- Публічний `/partner-docs`, JSON `/partner-openapi.json`: include лише
  PartnerApiModule; адмінські контролери живуть в окремому модулі.
- Ліміти на один процес: 300/хв/IP до авторизації, 60/хв/токен після неї, спільно для всіх партнерських маршрутів;
  без internal-token bypass; 429 + Retry-After. Для реплік потрібне спільне сховище.
- Без кешу авторизації: відкликання діє з наступного запиту (вже розпочатий
  запит може завершитися). Timestamp використання оновлюється не частіше разу/хв.

Перевірка: HTTP-контракт, RBAC, відхилення токенів, розділення лімітів,
ізоляція Swagger, хешування; збірка BE, перевірка типів FE та UI-сценарій.
Специфікації експортуються в Nest preview mode без підключення до MongoDB
та запуску служб. Інструкція інтеграції: `fillando-be/src/docs/PARTNER_API.md`.

## Каталог партнерів — розширення першого етапу

- POST `/partner/v1/categories`: плоский список, parent_id=null, sku_count,
  включно з порожніми категоріями. Підкатегорій у поточній схемі немає.
- POST `/partner/v1/products/skus`: category_id optional, limit 1–100,
  cursor із попереднього next_cursor; `{items: string[], next_cursor}`.
  Курсор base64url JSON v1 містить останній SKU та category_id; непрозорий для
  клієнтів, перевіряється сервером. Це не авторизаційний секрет і не snapshot.
- POST `/partner/v1/products/lookup`: до 100 артикулів, `{items, not_found}`.
  Публічний allowlist: назва, HTML, категорія, характеристики, ознака варіанта,
  фото, URL, вага та наявність. Без цін і даних постачальника.
- PartnerCatalogRepository має спільний join для лічильників, SKU й lookup:
  active, наявний Product і Category, збіг category_id товару й варіанта.
  Непов'язані записи не дають розбіжностей між лічильником і каталогом.
- Окремий контролер і сервіс у тому самому PartnerApiModule, ті самі guards
  та спільні ліміти. Lookup має успадковану валідацію пакетного запиту.
- Тести: HTTP-контракт, валідація/авторизація, спільні квоти, реальна MongoDB
  для counts/joins/cursor/allowlist; Swagger включає всі п'ять партнерських маршрутів.

POST `/partner/v1/products/skus` приймає category_id, cursor і limit у JSON body.
GET для категорій та SKU видалено. Категорії приймають порожній JSON-об’єкт {}.
Порожній body-об’єкт {} означає весь каталог, limit=100. limit у JSON — число.
